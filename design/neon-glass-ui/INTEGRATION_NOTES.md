## 判断が必要な論点（4つ）

実装前に、少なくとも次の4つは決めておく必要がある。
どれも技術的な細部ではなく、**製品の見た目と手触りの方向を決める**問いである。

### 1. ライト先行という決定と、ネオンガラスは噛み合うか

**これが最大の論点。**

Echo は [PRODUCT_VISION.md](../../docs/PRODUCT_VISION.md) の方針としてライトを主設計に選び、
暖かい紙のような背景（`#FBF9F7`）に、アクセント色を**あえて希少に**使う設計にしてある。
アクセントが希少だからこそ、アクセントが出た瞬間に意味が生まれ、触覚と一致させられる。

NEON GLASS は暗い背景に光が乗ることを前提とした表現である。
README も基準色の例として `Color.rgb(6, 11, 26)`（ほぼ黒紺）を挙げている。

したがって、素直に組み合わせると次のどちらかになる。

| 選択 | 意味 |
|---|---|
| **A. ダーク主設計へ切り替える** | ガラスが最も映える。ただしライト先行の決定を覆すことになる |
| **B. ライトのままガラスを使う** | 明るい下地でのガラス表現は別途詰める必要がある。未検証 |
| **C. 部分的に使う** | 暗い面（リアクションピッカー、スタンプパネル、モーダル）だけガラスにする |

**C が最も現実的**に見えるが、これは「見た目の統一感」を捨てる判断でもある。
**開発者本人が決めるべき論点であり、こちらで勝手に選ばない。**

### 2. View ベースと Compose の接続

NEON GLASS は `Drawable` と `View` で書かれている。Echo は全面 Jetpack Compose である。

Compose から使うには `AndroidView` で包むことになるが、
**これをメッセージバブル1つ1つに適用してはいけない。**
`LazyColumn` の各行に View を生成することになり、リサイクルとインタロップのコストが
スクロールに直撃する。Echo の中心価値がスクロールの滑らかさである以上、これは本末転倒になる。

現実的な適用先は、**数が少なく、生存期間が長い大きな面**に限られる。

```
✅  背景（LiquidBackdropView）
✅  コンポーザーのバー
✅  トップバー
✅  スタンプパネル
✅  リアクションピッカーのピル
✅  設定画面のカード

❌  メッセージバブル（数百個、スクロールする）
❌  リアクションチップ（小さい。§4も参照）
```

将来的に AGSL シェーダーを Compose の `RenderEffect` / `ShaderBrush` へ移植する道もあるが、
**それは移植であって組み込みではない。** 別作業として見積もる。

### 3. minSdk の不一致

| | 値 |
|---|---|
| Echo の現在の minSdk | **24**（Android 7.0） |
| NEON GLASS の要求 | **29**（Android 10）以上 |
| 屈折が効く条件 | **33**（Android 13）以上 + ハードウェア描画 |

選択肢:

- **minSdk を 29 へ上げる** — 2026年時点で実害はほぼ無い。ただし「Android 7 以上で使える」という
  現在の決定を変えることになる
- **24 のまま、29 未満ではガラスを使わない** — クラスは `@RequiresApi` で守られているので技術的には可能。
  ただし**端末によって見た目が根本的に違う**製品になる

なお API 33 未満では屈折が消えて塗りへ退避する（クラッシュはしない）。
つまり **29〜32 の端末では「ガラスに見えないガラス」**になる。
デザイン言語として成立するかは実機で見て判断すること。

### 4. GPU 予算と、この製品の中心価値

README にある実測値:

> NEON INSTINCT では中央値 9ms（120Hz の1フレームは 8.3ms）

**すでに 120Hz の予算を超えている。**
NEON INSTINCT はゲームであり、その代償を払う価値がある。

Echo の合格条件には「スクロールが指に貼りついて感じられる」が入っている。
**ここを削ってまで見た目を取る判断は、この製品の前提と矛盾する。**

したがって組み込むなら、**先に測ってから決める**。

```bash
adb shell dumpsys gfxinfo jp.echo.android.debug reset
# 8秒ほどスクロールする
adb shell dumpsys gfxinfo jp.echo.android.debug | grep -E "Janky|gpu percentile"
```

Pixel 10 は 120Hz なので、フレーム予算は 8.3ms。
**ガラスを入れる前と後で測り、差を見る。** 悪化したら面を減らす。

## 結論と提案（2026-08-15）

論点1について、**移植ではなく適用範囲の絞り込みで解く**ことを提案する。

### なぜ「ライト版へ再設計」が素直に効かないか

NEON GLASS の効果の材料は **背後にあるもの** である。縁が背景を屈折させることでガラスに見える。

Echo のライト背景はほぼ一様な `#FBF9F7` である。
**一様な面を屈折させても何も起きない。** クリーム色の上のクリーム色になるだけで、
色を差し替えても解決しない。

では背景に模様やグラデーションを敷けばよいかというと、そこで
**文字を読む時間が長いアプリの読みやすさ**を削ることになる。
README 自身が SHEEN と BLOOM を下げるよう勧めているのは同じ理由による。

### 提案: ガラスは「ページ」ではなく「ページの上に浮くもの」に載せる

Echo には、**背後に本物の内容があり、かつスクロールしていない面**がすでにある。

| 面 | 背後にあるもの | スクロール中か | 判定 |
|---|---|---|---|
| **リアクションピッカーのピル** | 暗転したスレッド | いいえ | ◎ 最有力 |
| **スタンプパネル** | スレッド | いいえ | ○ |
| トップバー / コンポーザー | スレッドが下を流れる | **はい** | △ 別途測る |
| メッセージバブル | — | はい | ✕ |
| ページ背景 | 何もない | — | ✕ 材料がない |
| リアクションチップ | — | — | ✕ 72px 未満 |

**読む面（スレッド本体）は紙のまま。ガラスは意図的に呼び出したものの上にだけ出る。**
これなら「メッセージ最優先」と衝突しない。

### これは妥協ではなく、むしろ独自性が出る

暗い背景に frosted glass は各社がやっている。
**暖かい紙の上に、操作した瞬間だけ現れるガラス**はほとんど例がない。

しかも触覚の思想と直結する。リアクションピッカーが出る瞬間は
すでに `SoftConfirm` が鳴る瞬間である。**視覚・素材・触覚が同じ一点に揃う。**

### 性能について

スクロール中のフレームに**ガラスが1枚も乗らない**構成なので、
「スクロールが重くなる」形の劣化は原理的に起きない。

- ピッカー / パネル: 表示は一瞬で、その間リストは止まっている
- トップバー / コンポーザー: **ここだけはスクロール中も毎フレーム合成される。**
  面積は小さいが、**第2段階として分けて測る**

### minSdk はライトのほうが有利

API 33 未満では屈折が消えて塗りへ退避する。
暗いネオン UI では「壊れて見える」が、**ライトでは半透明パネルとして自然に見える。**
したがって minSdk 24 のままでよく、29 へ上げる必要はない。→ 論点3は解決

### 進め方（最小の実験から）

1. **スクロール描画のベースラインを測る**（ガラスを入れる前の数値。これが守るべき基準）
2. **リアクションピッカーのピルだけ**をガラスにする
3. 見た目を実機で判断する。同時に測り直す
4. よければスタンプパネルへ広げる
5. トップバー / コンポーザーは**別段階**として、改めて測ってから決める

> **撤退条件を先に決めておく: 測定値が悪化したら戻す。**
> 見た目のために「スクロールが指に貼りついて感じられる」を削らない。

### ベースライン実測値（2026-08-15 / Echo 0.2.0 / ガラス導入前）

Pixel 10、46件のスレッドを約8秒スクロール。**パネルは 120Hz 駆動**
（`mActiveRenderFrameRate=120.00001`）なので **1フレームの予算は 8.3ms**。

| 指標 | 値 |
|---|---|
| 描画フレーム数 | 419 |
| **Janky frames** | **7（1.67%）** |
| 50th percentile | **6 ms** |
| 90th percentile | **11 ms** |
| 95th percentile | 15 ms |
| 99th percentile | 31 ms |
| Missed Vsync | 2 |

**GPU の内訳（0.2.1 の再測定で判明。これが判断を変える）**

| 指標 | 値 |
|---|---|
| 50th gpu percentile | **1 ms** |
| 90th gpu percentile | **2 ms** |
| 99th gpu percentile | **2 ms** |

**読み取れること:**

- 中央値 6ms は 8.3ms の予算内。通常のフレームは間に合っている
- 90th が 11〜12ms で予算を超えている。約1割のフレームは落ちている
- **ただしその遅さは GPU ではない。GPU は 99th でも 2ms しか使っていない。**
  現在のボトルネックは UI スレッド側であり、**GPU には 6ms 以上の余裕がある**

> **訂正:** 当初「余裕が薄いのでガラスは厳しい」と書いたが、これは総フレーム時間だけを見た
> 誤った読みだった。NEON INSTINCT の 9ms は GPU 律速の数値であり、Echo の 11ms とは
> 意味が違う。**ガラスが消費するのは主に GPU 時間であり、そこは空いている。**

したがって「スクロール中のフレームにガラスを乗せない」は、
**性能上の絶対的な禁止ではなく、最初の一歩を安全側に倒すための方針**として扱う。

とはいえ UI スレッドが既に詰まっている以上、
スクロール中の面（トップバー / コンポーザー）へ広げる判断は
**必ず再測定してから**行うこと。順序は変えない。

再測定の手順:

```bash
adb shell dumpsys gfxinfo jp.echo.android.debug reset
# 46件のスレッドを8秒ほどスクロールする
adb shell dumpsys gfxinfo jp.echo.android.debug | grep -E "Janky|percentile|Missed"
```

**比較対象は上の表。** 50th と 90th が悪化したら戻す。

（`Number High input latency` は adb の合成入力で大きく出るため、この計測では無視してよい。）

## 組み込むときの手順（決定後に実行）

1. パッケージ名を `com.neonglass` → `jp.echo.android.glass` へ置換し、ディレクトリを移動
2. `:core:glass` モジュールを作る（`androidx.annotation` のみ依存）
3. `LiquidBackdropView` を Compose の最背面に `AndroidView` で敷き、`NeonGlassScene.setBaseColor` を渡す
4. **`NeonGlassTuning.Preset.QUIET` から始める** — README が明示的にメッセンジャー向けに推奨している。
   文字を読む時間が長いアプリでは `SHEEN` と `BLOOM` を下げたほうが読みやすい
5. 適用先を §2 の ✅ に限定する
6. GPU を測る（§4）

## 落とし穴（README より、Echo に効くもの）

- **小さい面では屈折が効かない**（短辺 72px 未満）。リアクションチップは対象外
- **包む View を足して見た目を作らない。** 元の View を制御するコードが包んだ側に届かず、
  「要素は消えたのに面だけ残る」事故が NEON INSTINCT で2回起きている
- `NeonGlassScene` はプロセス全体で1つ。背景を持たない画面ではガラスが塗りへ退避する
- 調整値を変えたら `invalidate()` を木全体へ流す必要がある
