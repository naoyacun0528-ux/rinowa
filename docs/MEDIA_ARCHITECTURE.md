# 画像・動画の送信 — 設計

**状態: 設計。実装は段階的に。**
最終更新 2026-08-17

`STICKER_ARCHITECTURE.md` の5原則は**一つも変えません**。
写真と動画は「大きいスタンプ」ではなく、**同じ規則が桁違いの大きさに当たったもの**です。

```
PROCESS ON DEVICE          端末で加工する。元ファイルをサーバーへ上げない
STORE ONCE                 同じ内容はクラウドに1つ
REFERENCE BY ID            メッセージが運ぶのは ID だけ
CACHE LOCALLY              一度取得したら端末に持つ
DOWNLOAD ONLY WHEN NEEDED  見られていないものを落とさない
```

---

## 0. 結論

| 決定 | 内容 |
|---|---|
| 保管場所 | **自前の XServer**（`echo.nextlab.blog`）。Cloud Storage は使わない |
| 宛名 | **内容ハッシュ**（SHA-256）。同じ写真は何度送っても1つ |
| 画像 | 端末で **長辺 2048px / WebP** に再エンコード。**EXIF は必ず捨てる** |
| 動画 | **段階1では送らない。** 理由は §6。まず画像を完成させる |
| 吹き出しの中身 | **極小サムネイル（3〜6 KB）をメッセージ自体に埋める** |
| 本体の取得 | **タップされたときだけ**。自動では落とさない |
| Direct | 相手が近ければ **サーバーを通さず直接渡す**（本命） |

**最初に作るのは「サムネイルだけ入った画像メッセージ」です。**
それだけで会話は成立し、通信量は1通あたり数キロバイトに収まります。

---

## 1. いちばん危ないのは容量ではなく EXIF

写真には**撮影場所の緯度経度**が入っています。

> **元ファイルをそのまま送ってはいけません。**
> 「家で撮った子どもの写真」を送るということは、家の座標を送るということです。

`ProfilePhotos.kt` は既にこれをやっています —
`Bitmap` にデコードして WebP で再エンコードするので、**EXIF は構造的に消えます**。
メタデータを「削除する」のではなく、**メタデータを持たない経路で作り直す**。
削除は忘れられますが、作り直しは忘れようがありません。

同じ方式を写真送信にも使います。

**捨てるもの**: GPS、端末名、シリアル、撮影日時、ソフトウェア名、顔検出領域。
**残すもの**: 向き（回転を適用済みのピクセルにする）。

---

## 2. 保管場所 — なぜ Cloud Storage を使わないか

| 案 | 判断 |
|---|---|
| Firestore の Blob | **不可。** 1文書 1 MB。写真1枚が入らない |
| Cloud Storage for Firebase | **保留。** Blaze（従量課金）必須。友人数人の試作で課金口座を持つのは早い |
| **自前 XServer** | **採用。** `push.php` / `download.php` で既に動いている場所 |
| P2P のみ | **不可。** 相手がオフラインのとき届かない |

Cloud Storage を避ける判断は `ROADMAP.md` のスタンプの項と同じ理由です。
**「Firebase にあるから使う」で採用しない。**

### 移行できる形にしておく

保管場所は `MediaRepository` の中だけの知識にします。
Cloud Storage へ移すとき、**他のどこも触らずに済む**ようにする。
スタンプで `StickerRepository` にやったのと同じことです。ID 経由にした意味はここにあります。

## 3. 宛名は内容ハッシュ

```
mediaId = SHA-256(加工後のバイト列)
```

これで **STORE ONCE** が自動的に成立します。

- 同じ写真を3人に送っても、サーバー上は1つ
- 転送されても1つ
- **アップロードの前に「このハッシュ持ってる？」と聞ける**（`ADAPTIVE_TRANSPORT` §3.2）。
  持っていれば**アップロード自体が要りません**

そして**完全性が無料で付いてきます**。落としたバイト列のハッシュが ID と一致しなければ、
それは頼んだものではないので捨てる。サーバーを信用する必要がありません。

### 内容ハッシュの副作用（承知の上で使う）

同じ写真を送った2人は、同じ ID を要求します。
つまり**サーバーは「この2人は同じ画像を持っている」と分かります**。

これは重複排除を採る以上避けられません。隠さずに書いておきます。
本文が読めないことと違って、**これはルールで防げない種類の情報**です。
気になる規模になったら、per-user のソルトを入れて重複排除を捨てる、という交換になります。

---

## 4. メッセージが運ぶもの

```
image {
  mediaId    : 32 bytes   内容ハッシュ
  width      : varint
  height     : varint     受け取る前に場所を空けるため
  bytes      : varint     本体の大きさ。落とす前に「3.2 MB」と出せる
  blurThumb  : 3-6 KB     ★ここだけ本体を埋める
}
```

### なぜサムネイルだけ埋めるのか

**空の四角が並ぶ会話は、会話に見えないからです。**

本体を待ってから表示すると、電波の悪い場所では灰色の箱がしばらく残ります。
かといって本体を自動で落とすと、**見てもいない写真で通信量を使います**。

極小の WebP（長辺 32px、3〜6 KB）をメッセージ自体に入れると、
**受信した瞬間に、ぼやけてはいるが「何の写真か分かる」ものが出ます。**
本体はタップされたときだけ。

Yosegi v1 はこれをそのまま運べます — 長さ付きバイト列のフィールドを1つ足すだけで、
**未知フィールドとして旧クライアントは読み飛ばせます**（`YOSEGI_V1_SPEC.md` §5.5）。

サイズ感: 本文だけのメッセージが 47〜99 B。サムネイル込みで **4〜7 KB**。
本体は **200〜600 KB**。**2桁違う**ので、この分割には意味があります。

## 5. 取得の順序

`ADAPTIVE_TRANSPORT.md` §3 と同じです。

```
1. 端末のキャッシュ      ハッシュ一致 → 通信ゼロ
2. Direct の相手         近くにいる → サーバーを通さない
3. サーバー              どちらも無い → 落とす
```

**2 が本命です。** 家族が同じ部屋にいるとき、写真がインターネットを往復する理由はありません。

### 落とす条件

| 状況 | 動き |
|---|---|
| タップされた | 落とす |
| Wi-Fi で、設定が「自動」 | 落とす |
| モバイル回線 | **落とさない。** サムネイルのまま |
| 相手が Direct で繋がっている | Direct から取る |

**既定は「落とさない」**。`DOWNLOAD ONLY WHEN NEEDED` は設定項目ではなく既定値です。

## 6. 動画を段階1でやらない理由

作れないからではなく、**画像を完成させる前に始めると両方中途半端になる**からです。

動画には画像に無い問題が全部あります。

| 問題 | 中身 |
|---|---|
| 大きさ | 1分の動画が 50〜200 MB。XServer の共有ホスティングでは現実的でない |
| 再エンコード | `MediaCodec` で解像度とビットレートを落とす。端末ごとに挙動が違う |
| 時間がかかる | エンコードに数十秒。**その間アプリを閉じられたらどうするか**を決める必要がある |
| 途中再開 | 200 MB のアップロードが 95% で切れたとき、最初からやり直すのは論外 |
| 再生 | ExoPlayer/Media3 の追加。APK が数 MB 増える |
| サムネイル | 動画から1コマ取り出す。これは画像の仕組みで足りる |

**段階2で扱います。** その時の方針だけ先に決めておきます。

- **720p / H.264 / 2 Mbps 前後に再エンコード**して送る。原寸は送らない
- **上限を設ける**（例: 60 秒）。無制限は保管も転送も破綻する
- **Direct が繋がっているときだけ長い動画を許す**、という手はある。
  サーバーを経由しないなら容量の問題が消えるので
- アップロードは**再開可能**にする。これは設計段階で決めないと後から入らない

## 7. サーバー側（XServer）

`server/media.php`。既存の `push.php` と同じ作りにします。

```
POST /media.php
  Authorization: Bearer <Firebase ID token>     ← 本文ではなくヘッダ
  X-Rinowa-Media-Id: <sha256 hex>
  body: 加工済みバイト列

GET /media.php?id=<sha256 hex>
  Authorization: Bearer <Firebase ID token>
```

### 守ること

1. **ID トークンの署名を Google の証明書で検証する。** `push.php` と同じ手順
2. **サーバーがハッシュを検証する。** 宣言と中身が違うものは受け取らない
3. **上限を設ける。** 1ファイル 2 MB、1ユーザー 200 MB（段階1）
4. **拡張子で判断しない。** マジックバイトで WebP/JPEG/PNG を確認する
5. **ディレクトリを分ける。** `ab/cd/abcdef...` の2段。1階層に数万個置かない
6. **`Content-Type` は `application/octet-stream`。**
   ブラウザに解釈させない。`download.php` と同じ理由
7. **ブログのファイルには一切触らない**

### 誰が取れるかをどう制限するか

**段階1では「ログインしていれば取れる」にします。** ハッシュを知っている必要があります。

これは弱い保護です。正直に書いておきます:
ハッシュが漏れれば、会話の参加者でなくても取れます。
本来は「この mediaId を含むメッセージのある会話の参加者だけ」にしたいのですが、
それをやるには **PHP から Firestore を読む**必要があり、`push.php` で既にやっている
（会話の参加者確認）ので**不可能ではありません**。

**段階1.5でやります。** 段階1で出さない理由は、
サムネイルだけの状態では本体が存在しないので、実害が出る前に閉められるからです。

## 8. 端末内の保管

`LocalStickerStore` と同じ形にします。

```
filesDir/media/<hash の先頭2文字>/<hash>
filesDir/media/thumb/<hash>
```

- **ハッシュを検証してから保存する。** 一致しないものは捨てる
- **LRU で上限を設ける**（例: 500 MB）。写真は無限に増える
- **サムネイルは消さない。** 数キロバイトなので、消しても得が無く、
  消すと会話が空の四角になる

## 9. 実装の順序

| # | 内容 | できること |
|---|---|---|
| **M-1** | 画像の選択 → 端末内で加工（縮小・WebP・EXIF 除去）→ サムネイル生成 | 何も送らずに検証できる |
| **M-2** | `MediaContent` をモデルとメッセージに追加、サムネイルだけで表示 | **会話に写真が出る** |
| M-3 | `server/media.php` と `MediaRepository`、本体のアップロード | 相手が本体を見られる |
| M-4 | タップで取得、進捗表示、失敗時の再試行 | 実用 |
| M-5 | 事前問い合わせ（持っていれば上げない） | 通信量が桁で減る |
| M-6 | Direct から取る | 近くならサーバー不要 |
| M-7 | 会話参加者に限る取得制限（§7） | 段階1.5 |
| M-8 | 動画（§6） | 段階2 |

**M-1 と M-2 だけで「写真が送れる」ように見えます**（実際にはサムネイルだけ）。
そこで一度手を止めて、実機で見てから先に進みます。

---

## 10. やらないこと

- **元ファイルをアップロードしない。** 例外なし
- **見られていない画像を自動で落とさない**（Wi-Fi + 明示設定を除く）
- **画像を解析しない。** 顔認識も、被写体分類も、OCR もしない。
  それは「押しつけるコンテンツを作らない」「本文を分析しない」と同じ話です
- **サムネイルを Analytics に渡さない。** 画像は本文です

## 11. 実装後の訂正 — 2026-08-20

**この文書の §3 は、実装した結果、判断が覆りました。**
上を書き換えるのではなく、何がなぜ変わったかを残します。

### 11.1 保管場所は XServer になった（実装済み・実機で確認）

§2 の予定どおりです。ただし **暗号化してから置きます**。

| | 以前 | 現在 |
|---|---|---|
| 置き場所 | Firestore の Blob | `/home/nextlab/echo-media/`（web root の外） |
| 中身 | そのままのバイト列 | **暗号文のみ** |
| 鍵 | なし | ファイルごとに乱数32バイト。**封筒（E2EE）の中を通る** |
| 範囲取得 | できない | `Range:` 対応（動画ストリーミングの前提） |

鍵がメッセージ文書ではなく**封筒の中**にあることが要点です。
文書に置けば、データベースを読める者は誰でも全部の写真を開けます。
それはこの保管場所が塞ごうとした穴そのものでした。
封筒の中なら、**そのサーバーを運用している人間にも読めません**。

暗号方式は Tink の AES-GCM-HKDF-STREAMING（STREAM 方式）。
1 MB ごとに認証タグが付くので、**バイト範囲だけを取り出して復号できます**。
独自の形式は作っていません（PRIVACY_PRINCIPLES.md の禁止事項）。

古い写真は Firestore に残っており、そのまま読めます。
鍵を持たないメッセージがそれです（`MediaRepository.fetch`）。

### 11.2 §3 の重複排除は、やめました

内容ハッシュによる重複排除は、**同じ平文が同じ暗号文になること**を必要とします。
つまり鍵を平文から導く必要があり、そうすると
**「この2人は同じ写真を持っている」がサーバーに分かります**。

§3 の「内容ハッシュの副作用（承知の上で使う）」で既に名前を付けていた代償です。
保管場所が暗号化された今、その代償を払う理由がなくなったので、**逆の取引をしました**。

- 鍵はファイルごとに乱数。同じ写真でも暗号文は毎回違う
- したがって ID も違う。**送信者をまたいだ重複排除は無い**
- 1回の送信の中では、アップロード前に存在確認をするので無駄な送信は起きない

`mediaId` は**暗号文の** SHA-256 です。サーバーは中身を読めないまま、
受け取ったものが名乗ったとおりかを検証できます。

### 11.3 §10「元ファイルをアップロードしない」は、そのまま生きています

一度は「30日だけ元ファイルも預かる」設計に傾きました（media_common.php の orig クラス）。
**採用しません。** 指示は「オリジナルはサーバーに保存せず圧縮版だけクラウド保存」でした。

正直に書いておくべき帰結:

> **元ファイルは、撮った端末にしかありません。**
> 送った側は自分のものなので「オリジナルで保存」できます。
> 受け取った側にあるのは圧縮版だけで、選ぶものがありません。

サーバー側の orig クラスは残っていますが、**クライアントは一度も使いません**。

### 11.4 サムネイルも封筒の中に入りました

以前はメッセージ文書に直接埋めていました。3〜6 KB の 32px です。
小さくても**それは写真そのもの**なので、封筒の外に置けば
「写真の説明文だけ暗号化して写真は平文で送る」ことになります。

いまは ID・大きさ・バイト数・サムネイル・鍵の全部が封筒の中です。
文書の外に出ているのは、誰が・いつ送ったか、それだけです。
