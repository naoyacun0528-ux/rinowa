# 形式の仕様 — 封筒・バックアップ・メディア

**この文書は契約です。** 実装が2つ以上あるとき、両方が同じ解釈をしなければならない部分だけを書きます。
UI も通信も入りません。

対になるのが `research/vectors/formats.json` です。
文章は読み方を説明し、**ベクタが正解そのもの**です。食い違ったらベクタが勝ちます。

最終更新 2026-08-23

---

## 0. なぜ文章とデータの両方があるか

形式のずれは静かに壊れます。フィールド名が1つ違うだけで、
**他は完全に正常に見える端末の、古いメッセージだけが開かなくなる**。
しかも気付くのは、たいてい送った本人ではなく相手です。

だから2つ用意しています。

| | 役割 |
|---|---|
| この文書 | なぜその形なのか。判断の理由 |
| `research/vectors/formats.json` | 何が正しいか。**機械が検証できる形** |

ベクタは `FormatVectorsTest`（Android）が生成し、以後は検証だけします。
別の実装は、同じファイルを読んで同じ結果を出せなければなりません。

**方向は読み取り側に固定しています。** 「この内容からこのバイト列を作れ」ではなく
「**このバイト列をこう解釈しろ**」。正しい JSON 実装同士でもキーの順序は違うので、
出力を固定すると*正しい実装が落ちて*、肝心の食い違いは見逃します。

## 1. 封筒（MessageEnvelope）

暗号化される中身。Megolm で封をする前の平文が、この JSON です。

### 1.1 なぜメッセージ全体を包むのか

最初は本文の文字列だけを暗号化していました。写真を送った瞬間に破綻します:
ID・寸法・**サムネイル**が封筒の外に出ます。32px でも、それは写真そのものです。
**写真の説明文だけ暗号化して写真を平文で送るのは、暗号化ではなく装飾です。**

いま外に出ているのは「誰が・いつ送ったか」だけです。

### 1.2 共通

- UTF-8 の JSON オブジェクト1つ
- バイト列は **Base64（RFC 4648 標準、パディングあり）** の文字列
- 未知のキーは**無視する**。将来の追加を古い実装が壊さないため
- 未知の `t` は**メッセージ1件を諦める**。スレッド全体を落とさない

### 1.3 種類ごとのキー

| `t` | キー | 意味 |
|---|---|---|
| `text` | `b` | 本文（文字列） |
| `image` | `id` | メディアID（**暗号文の** SHA-256、小文字16進64桁） |
| | `k` | メディア鍵 32バイト、Base64 |
| | `w` `h` | 表示上の幅・高さ（整数） |
| | `n` | 圧縮版のバイト数 |
| | `th` | サムネイル（WebP、長辺32px）、Base64 |
| | `oid` `ok` `on` `om` | オリジナルの ID・鍵・バイト数・MIME（**任意**） |
| `video` | `id` `k` `w` `h` `th` `n` | image と同じ意味 |
| | `ms` | 長さ（ミリ秒） |
| | `sn` | **暗号文の**バイト数。範囲取得の再生に必要 |
| `sticker` | `s` | スタンプID |
| `call` | `v` | ビデオ通話なら true |
| | `o` | `completed` / `missed` / `declined` / `failed` |
| | `sec` | 通話秒数（`completed` のときだけ意味を持つ） |

`w` `h` は**表示される形**です。保存された形ではありません。
縦で撮った動画は「横のフレーム＋90度回せ」で保存されることが多く、
保存値をそのまま使うと**縦の動画に横の場所を用意する**ことになります。

### 1.4 開けなかったときの規則

1. JSON として読めない → **全体を本文とみなす**（封筒より前に送られたメッセージ）
2. JSON だが `t` が未知 → **全体を本文とみなす**（誰かが JSON を打っただけ）
3. `th` や `k` の Base64 が壊れている → その項目だけ空にして、残りは読む

1 は互換性のためです。研究用のビルドでも、**読めるメッセージを黙って失うのは、
この形式が何を保証するかについて誤った教訓を残します**。

## 2. バックアップ（BackupCipher / BackupArchive）

### 2.1 ファイル

```
オフセット  長さ  内容
0          8    "LOWANBK" + 0x01        マジックと版
8          4    反復回数（ビッグエンディアン int32）
12         16   ソルト
28         12   ノンス
40         n    AES-256-GCM の暗号文（末尾16バイトが認証タグ）
```

- 鍵導出: **PBKDF2-HMAC-SHA256**、既定 **600,000** 反復、256ビット
- **先頭40バイトを AAD として認証に含めます**
- 復号時、反復回数が 100,000 未満または 10,000,000 超なら**読まずに拒否**

AAD が要点です。総当たりを安くする一番簡単な手は**ヘッダの反復回数を下げること**で、
AAD に含めておけば、それは復号失敗になります。書き換えても弱くなりません。

### 2.2 中身

```json
{ "v": 1, "owner": "<uid>", "at": <ミリ秒>, "messages": [
  { "c": "<会話ID>", "m": "<メッセージID>", "s": "<送信者ID>",
    "t": <ミリ秒>, "e": "<封筒の平文>" } ] }
```

`e` は §1 の封筒そのものです。**エンコーダは1つ**で、写真が復元で生き残る理由は
送信で生き残る理由とまったく同じになります。形式が2つあれば、いつか片方だけ直ります。

`v` が読める版より大きければ**半端に読まずに拒否**します。
会話の一部だけが戻る復元は、戻らない復元より悪いからです。うまくいったように見えるので。

### 2.3 正直な限界

**6桁の数字は100万通りです。** どんな鍵導出もその数を大きくしません、1回を高くするだけです。
60万反復で端末なら1推測1秒前後。**ファイルを持っていて本気の相手なら通ります。**

買えているのは「Drive のアカウントをたまたま握った人には読めない」ことと、
長い合言葉なら本当に強いこと。設定画面はそう書いてあり、数字を勧めていません。

## 3. メディア（MediaCipher）

- 方式: **AES-GCM-HKDF-STREAMING**（Tink の STREAM 実装）
- HKDF: HMAC-SHA256、鍵 32バイト
- セグメント: **1 MiB**、最初のセグメントのオフセット 0
- AAD: `rinowa-media-v1`（ASCII）
- `mediaId` = **暗号文の** SHA-256、小文字16進

セグメントごとに認証タグが付くので、**バイト範囲だけを取り出して復号できます**。
動画をダウンロードし切らずに再生できるのは、これが理由です。

**iOS への移植で最初に確認すべき点がここです。** Tink の Streaming AEAD は
Obj-C バインディングに**ありません**。C++ を噛ませるか、この形式を見直すかの判断が要ります。
見直す場合、**既に送信済みのメディアが読めなくなる**ので、版を分ける必要があります。

## 4. 変えるときの手順

1. この文書を直す
2. `research/vectors/formats.json` を**消してテストを走らせる**（現在の実装から再生成される）
3. 差分を読む。**意図した差分だけが出ているか**を目で確認する
4. 他の実装のテストを走らせる

2 を「テストが赤いから消す」ためにやってはいけません。
消すというのは「**今日の挙動を正しさの定義にする**」という決定です。
ベクタが落ちたとき、間違っているのはたいていテストではありません。
