# 弱いモーターに届かない

2026-09-05。arrows We2 で触覚がほとんど感じられない件を調べた記録。

**結論から: 能力の検出は正しく動いている。問題はその先にある。**

## 分かっていること

We2 は Android 16（API 36）で、API の上では最上位に届く。だが**モーターが安い**ので、
実際に出る振動は最下位相当。

`detectCapabilities` はハードウェアにきちんと問い合わせている。

```kotlin
vibrator.hasAmplitudeControl()
vibrator.areEnvelopeEffectsSupported()   + envelopeEffectInfo
vibrator.arePrimitivesSupported(...)
vibrator.areEffectsSupported(...)
```

能力が無ければ自動で段が落ちる。**そこは設計どおり動いている。**

## それでも届かない理由

### 1. 問い合わせは「できるか」しか答えない

`areEnvelopeEffectsSupported()` が true なのは「ドライバが Envelope を受け付ける」
という意味であって、「強く出る」ではない。安い LRA でも、正しいドライバが載って
いれば true を返す。

**「このモーターは弱い」を答える API は Android に無い。** 共振周波数も最大加速度も
取れない。問い合わせを増やしても拾えない。

### 2. 段を落としても弱くなるだけ

`Selection` を段ごとに並べると、下に行くほど弱い。

```
T4 Envelope       0.25
T3 PrimitiveRich  Tick x 0.25
T2 Primitive      Tick x 0.25
T1 Predefined     プラットフォームの Tick（固定・弱い）
T0 Waveform       8ms @ 40   = 0.157
```

**この梯子は表現力の梯子であって、強さの梯子ではない。** 仮に We2 が T1 まで落ちても、
もっと薄くなるだけで、届くようにはならない。

255 まで振り切る `onOff` は用意してあるが、入口が `hasAmplitudeControl == false` だけ。
We2 は強さを変えられるので、**永久にそこへ入れない。**

### 3. 最短が立ち上がりより短い

`Selection` は 8ms。ERM や安い LRA は回り切るまでに 20〜30ms かかる。
**回る前に終わっている可能性がある。** 未確認。

## 他所はどうしているか

学習アプリの触覚実装を1つ解析した（Pixel 10 / Android 17 で採取。素材は他者の
著作物なので持ち込まない。**学べるのは作り方だけ**）。同じ「押した」に3つの版がある。

| 版 | 端末 | 長さ | 強さ |
|---|---|---|---|
| OGG | 良いモーター | 27ms | -23dB（約 7%） |
| 中位向け | 中位 | 30ms | 128（50%） |
| 低位向け | 安いモーター | 30ms | **255（100%）** |

**モーターが安いほど強く叩いている。** 同じ効果で14倍の差。Rinowa は逆で、
下ほど弱くなり、上げる道が無い。

同じ効果でも単純な間引きではなく作り直されている。

```
強く短い:  110ms  Timings[50,30,30]  Amplitudes[255,0,255]
弱く長い:  200ms  Timings[100,100]   Amplitudes[77,128]
```

そして最短でも 30ms。8ms のものは1つも無い。

### 波形の中身（27ms の「押した」を 2ms 刻みで測った）

```
  0ms  -24.2dB  250Hz
  8ms  -23.9dB  250Hz
 16ms  -23.5dB  250Hz
 24ms  -23.0dB  250Hz
```

**減衰していない。** 一定の強さで 250Hz を 27ms 流して、ぶつ切りで終える。
クリック感を減衰ではなく**周波数**で作っている。`createWaveform` では周波数を
指定できないので、ここは Rinowa の道具では埋まらない。

### 長さの分布

解析した95件のうち、

```
100ms未満     9件
100-400ms     6件
400ms-1秒    16件
1-2.5秒      24件
2.5秒以上    40件
```

**半分近くが2.5秒以上の演出。** 静かな側（-23dB）は4件しかない。

**メッセンジャーはこの分布が逆になる。** 1日数百回来るものを、1日数回の達成と
同じ強さで鳴らしたら、ただの故障。取るべきは演出ではなく、**あの4件の質**。

## 途中で見つかった別の穴

**強さの設定は前からあったのに、覚えていなかった。**

```
RinowaApplication.kt:257   起動時に読む        settings.localHaptics()
HapticLabScreen.kt         変える（メモリだけ） haptics.setPreferences(...)
putLocal(haptics = ...)    ← 呼び出し 0
```

`SettingsRepository.putLocal(haptics = ...)` は実装済みで、**呼ぶ人がいなかった。**
実験室でつまみを動かすとその場では効くが、次の起動で元へ戻っていた。

そして触れる場所が実験室だけだった（一覧の隠し操作から開く画面）。
**普通に使っている人は辿り着けない。**

## 打ち手

モーターの強さは測れないので、賢く判定する道は無い。

### 済み（2026-09-05）

**A. 強さの設定を人に出した。** アカウント画面に4段（なし／弱／標準／強）。
押すとその強さで1回鳴るので、違いをその場で確かめられる。あわせて
`putLocal(haptics = ...)` を繋いで、**覚えるようにした。**

**C の前半。** 実験室に「立ち上がり」の物差しを足した。8 / 12 / 16 / 24 / 32 /
48 / 64ms を順に押せる。`previewPulse` はトークンも段も通さない生の指示で、
**強度のつまみも掛けていない**——短くて出ないのか、弱くて出ないのかを分けるため。

### 未着手

**B. `onOff` の入口を広げる**
設定が「強」のとき、`hasAmplitudeControl` に関係なく 255 を使う。
いま `onOff` を持っているのは12個中3個だけなので、足りないぶんを書く必要もある。

**C の後半。最短を伸ばす**
8ms を何ミリ秒へ伸ばすか。**数字はまだ決めていない。**
arrows We2 で物差しを押して、最初にはっきり分かるところが答え。
当てずっぽうで 24ms にするより、測ってから決める。

**D. 触覚 OGG（後回し）**
`SoundPool` + 3ch OGG（ch1 に触覚、`ANDROID_HAPTIC=1`）。API 29 から使えて
Envelope（API 36）より対応が広く、周波数も動かせる。`MediaPlayer` では
触覚チャンネルがミュートされるので使えない。

**ただし効くのは良いモーターだけ。** 250Hz と 150Hz を撃ち分けられないモーターに
任意波形を渡しても同じなので、**We2 には何も効かない。** 順番としては最後。

## 教訓

この調査で2回、間違った結論を出した。

1. 「段の決め方が API しか見ていない」と書いたが、実際にはハードウェアに
   問い合わせていた。**コードを読む前に、症状から原因を決めていた。**
2. 「強さの設定は無い」と書いたが、あった。**grep のパスを間違えて、空の結果が
   返ったのを「無い」と読んだ。** 空の結果は、無いことの証明ではない。

どちらも、なおやさんの指摘か自分の再確認で気づいた。**確かめてから言う。**
