# PRODUCT VISION

## 中心思想

1. **メッセージングそのものを最優先する**
2. **UI・操作性・触覚を非常に重視する**
3. **ユーザーフィードバックを開発の中心に据える**
4. **不要なコンテンツや機能を押し付けない**
5. **ユーザーのプライバシーを侵害しない**
6. **AI を使ってフィードバックを高速に改善へ反映できる構造にする**

## この製品が目指すもの

LINE を機能数で上回ることは目標ではない。

目標は、

> **「LINE があるのに、こっちを触りたくなる」**

という状態である。

メッセンジャーは1日に何十回も開かれる。だからこそ、1回あたりの操作の気持ちよさの差が、
機能の差より大きく効く。この製品はそこに賭ける。

## 作らないもの

意識的に作らないものを先に決めておく。これは制約ではなく、製品の輪郭である。

- **タイムライン / ニュース / おすすめ / 広告枠**
  メッセージを読みに来たユーザーに、メッセージ以外を見せない。
- **開かせるための通知**
  「久しぶりに開いてみませんか」の類は作らない。通知は届いたメッセージのためだけにある。
- **滞在時間を伸ばすための仕掛け**
  用が済んだら閉じられるべき。滞在時間は成功指標ではない。
- **Web 版 / PWA**
  触覚表現が大きく制限され、ネイティブと比べて操作感が落ちる。
  最初の実験段階からネイティブアプリとする。
- **管理者がメッセージ本文を読める仕組み**
  → [PRIVACY_PRINCIPLES.md](PRIVACY_PRINCIPLES.md)

## スタンプは主要機能である

**スタンプを廃止しない。リアクションで完全代替しようともしない。**

LINE 等で実証されているとおり、スタンプは文章の代替ではなく独立した表現手段である。
「メッセージングを最優先する」ことは「文字だけにする」ことではない。

ただし独自の方向として、**巨大なスタンプショップを最初から用意するのではなく、
「自分たちで非常に簡単に作れる」ことを軸に置く。**

発展の方向:

- ユーザー自身によるカスタムスタンプ作成
- 友達共有 / グループ限定パック
- リアクション
- アニメーション表現
- **触覚を伴う Echo 独自の Expression**

最後の項目がこの製品固有の価値になりうる。
スタンプ + アニメーション + 触覚 を1つの表現として設計できるのは、
触覚を製品の中心に据えているからである。

→ [STICKER_ARCHITECTURE.md](STICKER_ARCHITECTURE.md)

> **ただし Prototype 段階で機能を増やしすぎない。**
> Prototype 0 で検証するのは「出す・選ぶ・送る・見える」の操作感だけ。

## 端末に依存しない

> **Device can be replaced. Account persists.**

端末が壊れても、機種を変えても、アプリを入れ直しても、
ログインすれば元に戻る構造にする。

「この端末でしか使えないアプリ」は、勧めた相手が機種変更した時点で失われる。
→ [SYNC_AND_BACKUP.md](SYNC_AND_BACKUP.md)

## 判断の優先順位

設計判断が衝突したとき、上にあるものを優先する。

1. **プライバシー** — 本文が漏れる設計は、他の何と引き換えでも採用しない
2. **メッセージが確実に届くこと** — 気持ちよさより先に、まず届く
3. **操作の気持ちよさ** — 触覚・視覚・アニメーション・音の一致
4. **機能の豊富さ** — 最も優先度が低い

## 触覚に対する立場

Duolingo の触覚設計に強い影響を受けている。

重要なのは **「振動をたくさん入れる」ことではない**。

> **操作の意味と、視覚表現と、触覚が対応していること。**

触覚が視覚と食い違うと、ユーザーは理由を言語化できないまま「安っぽい」と感じる。
逆に一致していると、理由を説明できないまま「良い」と感じる。後者を作る。

各画面から直接 Vibrate API を呼ぶ構造にはしない。
意味ベースの共通 Haptic Design System を通す。
→ [HAPTIC_DESIGN.md](HAPTIC_DESIGN.md)

## Android と iOS

UX 仕様は共通ドキュメントとして管理する。

ただし **UI を両 OS で完全一致させることは目標にしない。**
それぞれの OS で自然に感じられることを優先する。

特に触覚は、Android で調整した数値を iOS へそのまま移植してはならない。
振動子（Android: LRA/ERM の幅広い個体差、iOS: Taptic Engine）が根本的に異なる。
共有するのは **「意味」** であり、値ではない。

Android では Material の API を必要に応じて利用するが、
**見た目を単なる Material テンプレートにはしない。** 独自 UI を優先する。

## ユーザーフィードバックの位置づけ

単なる「お問い合わせフォーム」にはしない。アプリ開発そのものにユーザーを参加させる。

- Feature request / Bug report
- Feature voting / UI voting / Haptic voting
- 公開ロードマップ / Changelog
- β テスト / アップデート後アンケート

ただし **投票結果をそのまま全採用するのではない。**
投票、実際の利用データ、UX 上の整合性、技術的制約を合わせて判断する。

将来的には `Feedback #21 → RELEASED in Beta 0.4` のように、
自分の意見がどう反映されたかがユーザーから見える状態を目指す。

## 開発体制（Human-in-the-loop）

開発者本人はコードを書かない。実装・Git・ビルド・CLI は Claude Code が担当する。

開発者本人が担当するのは:

- 実際の画面を確認する
- 操作感を確認する
- Claude の作業方針を読む
- 意図と違う部分を指摘する
- UI・触覚・挙動について細かく修正指示を出す

### Claude Code への恒久的な制約

自走してよい。ただし以下は絶対に行わない。

- 仕様を勝手に大きく変えない
- **プライバシー制約を緩めない**（デバッグしやすいという理由でも緩めない）
- **本文を扱う Analytics を追加しない**
- **独自暗号を実装しない**
- セキュリティ警告を無視しない
- **実機で確認すべき UI / 触覚を、勝手に「完成」と判断しない**

## Prototype 0 の合格条件

Prototype 0 は機能の網羅では評価しない。以下だけで評価する。

- [ ] スクロールが指に貼りついて感じられる
- [ ] 送信した瞬間の視覚・触覚が一致していて、押し続けたくなる
- [ ] スワイプ返信の成立点が、見なくても指でわかる
- [ ] 長押し → リアクションの流れが途切れない
- [ ] 触覚が「多い」ではなく「合っている」と感じられる
- [ ] LINE を開いた直後にこれを開いて、戻りたくならない

このどれかが「まあまあ」なら、Prototype 1 へは進まない。
