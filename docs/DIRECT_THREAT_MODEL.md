## 0. 前提を1つ潰しておく

> **「P2P だからプライバシーが高い」は誤りである。**

サーバーを経由しないことで消える漏洩がある一方、**Direct が新しく作り出す漏洩がある。**
後者のほうが、この製品にとっては危険度が高い。

| Cloud にあって Direct で消えるもの | Direct が新しく作るもの |
|---|---|
| サーバーが本文を保持する | **誰が誰の近くにいたか** |
| サーバーが配信時刻を知る | **いつ・どこで Rinowa が起動していたか** |
| 事業者への開示請求で本文が出る | **どの端末を持っているか** |

**Direct を入れるということは、位置と人間関係に関する新しい面を作るということである。**
本文を守るために作った仕組みが、本文より復元しやすい社会グラフを漏らしては本末転倒になる。

---

## 1. 守る対象

優先順位つき。上が破られたら他が全部無意味になる。

1. **メッセージ本文** — 参加者以外が読めないこと
2. **社会グラフ** — 誰と誰が友達か、誰と誰が同じ場所にいたか
3. **在圏情報** — ある人がいつ・どこにいたか
4. **端末構成** — 何を何台持っているか
5. **可用性** — Direct の失敗がメッセージの消失にならないこと

---

## 2. 想定する攻撃者

| | できること | 動機 |
|---|---|---|
| **A. 受動的な盗聴者** | 電波を傍受する。同じ場所にいる | 誰がいるかを知りたい |
| **B. 能動的な近接攻撃者** | 偽の広告を出す。接続を試みる | なりすまし、データ取得 |
| **C. 追跡者** | 複数地点に受信機を置き、長期間記録する | 特定人物の移動を追う |
| **D. 悪意ある友達** | 正規の認証を通る | 相手の在圏を継続監視する |
| **E. 端末を盗んだ者** | 端末を物理的に持っている | 過去/将来の通信 |
| **F. Rinowa 運営（＝開発者自身）** | サーバーを持つ | ここも攻撃者として数える |

**F を数えるのが Rinowa の立場である。** [PRIVACY_PRINCIPLES.md](PRIVACY_PRINCIPLES.md) が
管理者の本文読み取り経路を構造的に否定しているのと同じ理由で、
Direct でも「運営なら知ってよい」を作らない。

## 3. 脅威と対策

### T1. 近接ユーザーの列挙（攻撃者 A / C）

**脅威。** 広告パケットを集めるだけで「この場所に Rinowa ユーザーが N 人いる」
「毎朝この端末が通る」が分かる。固定 ID を広告していれば、**それは追跡タグである。**

**対策。**

- 広告に載せる識別子は**回転させる**。固定 deviceId・uid・招待コードを平文で出さない
- 回転周期は追跡耐性と再接続性のトレードオフ。実装時に測って決める
- 友達だけが復元できる形にする（共有秘密からの導出）
- 表示名・メール・プロフィール画像は**絶対に広告に載せない**

**残る穴。** 電波が出ている事実そのものは隠せない。
「ここに Rinowa 利用者がいる」までは、どうやっても分かる。
隠せるのは「それが誰か」までである。**これを隠せると言わない。**

### T2. なりすまし（攻撃者 B）

**脅威。** 友達 B のふりをして接続し、メッセージを受け取る。

**対策。** [DIRECT_ARCHITECTURE.md](DIRECT_ARCHITECTURE.md) §6 の相互 Challenge-Response。
**近接は認証ではない。** 秘密鍵を持たない相手は通らない。

**やってはいけない対策。** 「同じ Wi-Fi にいるから信用する」「MAC が一致したから信用する」。
どちらも偽装できる。

### T3. 中間者（攻撃者 B）

**脅威。** A と B の間に入り、両者に対してそれぞれを名乗る。

**対策。** Transport の暗号化を、**認証済み identity に紐づける**。
鍵交換の結果と検証済み public key が一致しない接続は破棄する。

標準 TLS 相当 / OS 提供 secure transport を使い、**独自ハンドシェイクを書かない。**
中間者対策を自作して間違えるのは、この分野で最も多い失敗である。

### T4. 失効した端末（攻撃者 E）

**脅威。** 盗まれた端末が、まだ失効を知らないオフライン端末に対して正規の相手として通る。

**対策。** Cloud で revoke でき、オンラインの端末は即座に反映する。

> **残る穴（重要）。**
> **オフライン端末は失効を知らない。** 圏外の端末は、revoke された端末を信用し続ける。
>
> これは実装の不備ではなく、**「オフラインでも動く」と「失効が即座に効く」が
> 両立しないという構造的な帰結**である。緩和はできるが、消せない。
>
> 緩和案（実装時に選ぶ）:
> - Identity 情報に**有効期限**を持たせ、期限切れは再確認を要求する
> - 期限を短くするほど安全になり、オフライン耐性が落ちる。**この軸で調整する**
> - 端末紛失時、利用者に「オフラインの端末には反映が遅れる」と明示する
>
> **「失効すれば安全です」と言わない。** 言えるのは「オンラインの端末では即座に効く」まで。

### T5. 友達による在圏監視（攻撃者 D）

**脅威。** 正規の友達が、Direct の接続可否を使って「相手が今どこにいるか」を継続的に知る。
これは認証を破らない。**仕様通りに動いていても起きる。**

**対策。**

- Direct を **OFF にできる**こと（[DIRECT_ARCHITECTURE.md](DIRECT_ARCHITECTURE.md) §14）
- 接続の成立を**相手に通知しない**。「あなたは今 B の近くにいます」を出さない
- 継続的な近接ログを**端末にもサーバーにも残さない**
- 常時 Discovery をしない（§15）ことは、電池だけでなくここにも効く

**残る穴。** 送信が速いかどうかから経路を推測される可能性はある。
`⚡ Direct` 表示を**自分の画面にだけ出し、相手には出さない**ことで緩和する。

### T6. Telemetry からの再構成（攻撃者 F）

**脅威。** Direct の統計を集めるうちに、社会グラフや位置がサーバー側で復元できてしまう。

**対策。** [ANALYTICS_SCHEMA.md](ANALYTICS_SCHEMA.md) の規則を厳格に適用する。

**送ってはいけない:**

- 接続相手の識別子（uid / deviceId / 回転 ID を問わず）
- 接続時刻の**列**（集計値のみ。系列は移動履歴になる）
- 位置情報
- SSID / BSSID / Bluetooth アドレス

**送ってよい:** 成功率・遅延・バイト数・失敗理由の分類・端末の能力。

> 「Direct 接続が成立した相手の uid」は、**1つ送るだけで社会グラフになる。**
> 本文を守る型システムを作っておきながらここで漏らすのは、最も間抜けな失敗である。

### T7. Direct 経由での不正な payload（攻撃者 B / D）

**脅威。** 認証を通った相手が、壊れた/悪意ある payload を送ってクライアントを壊す。

**対策。**

- Direct から来たデータも、**Cloud から来たデータと同じ検証を通す**
- Asset は受信後に**サイズ上限とハッシュを検証**してから保存する
  （[STICKER_ARCHITECTURE.md](STICKER_ARCHITECTURE.md) の整合性検査をそのまま使う）
- 「認証済みの相手だから中身を信用する」をやらない。**認証は身元であって、内容の保証ではない**

### T8. 可用性の低下（構造的）

**脅威。** Direct を優先した結果、メッセージが届かなくなる。

**対策。** [DIRECT_ARCHITECTURE.md](DIRECT_ARCHITECTURE.md) §8.2 の fallback と
§2.1（Core Functionality を Direct に依存させない）。

**これは Direct における最大の失敗モードである。** 速さのために信頼性を落としたら、
メッセンジャーとして負けている。§17 で fallback 成功率を必ず測る。

## 4. 明示的に守らないもの

守れないものを守れると言わない。

| 守らない | 理由 |
|---|---|
| 電波の存在自体の秘匿 | 物理的に不可能 |
| 電波強度からの距離推定 | 誰でもできる |
| **オフライン端末への即時失効** | T4。構造的に両立しない |
| OS / ドライバの脆弱性 | Rinowa の層で対処できない |
| 端末が既に侵害されている場合 | 秘密鍵が守れない前提が崩れる |
| **Android ↔ iPhone の完全オフライン** | 脅威ではなく §0 の技術的制約 |

## 5. Message E2EE との関係

**Transport Encryption と Message E2EE を混同しない。**

- Direct Channel の暗号化は **経路の保護**。相手の端末に着いたら平文に戻る
- Message E2EE は **中身の保護**。サーバーも中継者も読めない

現時点の Rinowa は E2EE を持たない。だから **「Direct だから運営にも読めない」は正しいが、
それは Direct のときだけであり、Cloud 経路では成り立たない。**

利用者への説明でこの2つを混ぜない。混ぜた瞬間、説明が嘘になる。

## 6. 実装前に必ず再確認する

Direct-1 に着手する時点で、この文書を読み直して以下を確認する。

- [ ] 広告に固定識別子が入っていないか
- [ ] 認証を通る前に payload が流れる経路が無いか
- [ ] 失効の有効期限を決めたか。オフライン時の挙動を利用者に説明できるか
- [ ] Telemetry に相手の識別子・時刻列・位置が入っていないか
- [ ] Direct が落ちたとき、メッセージが消えずに Cloud へ回るか
- [ ] Direct を OFF にして、Rinowa が完全に動くか
- [ ] 独自の暗号方式・ハンドシェイクを書いていないか
