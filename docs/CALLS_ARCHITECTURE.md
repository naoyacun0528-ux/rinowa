# 音声通話・ビデオ通話 — 設計

**状態: 設計。実装は段階的に。**
最終更新 2026-08-17

---

## 0. 結論

| 項目 | 決定 |
|---|---|
| 方式 | **WebRTC**。他に選択肢は無い |
| 暗号 | **DTLS-SRTP**（WebRTC に内蔵・必須）。**自作しない** |
| 呼び出しのやりとり | **Firestore**。サーバーを新たに立てない |
| NAT 越え | STUN + **TURN は必ず用意する。** Cloudflare で開始、VPS へ移せる形に（§5） |
| 着信の起こし方 | **FCM の高優先度データ通知**。既存の `push.php` から |
| 段階1 | **音声のみ。** 同一 Wi-Fi なら確実に繋がる。TURN 投入で全回線を埋める |
| ビデオ | 段階4。コーデックは**ハードウェア符号化できる中で最良**（§5.5） |

**「たまに繋がらない通話」は「繋がらない通話」です。** だから TURN は必ず用意します。
ただし TURN を待つ必要はありません——**同一 Wi-Fi なら STUN すら要らずに繋がる**ので、
家の中の通話は今日から動きます。TURN が埋めるのは、その外側です。

**APK は 3.78 MB → 44.62 MB（全ABI）と実測済み。** ABI 分割で1台あたり約 14 MB。
通話が必須である以上、これは払う費用として受け入れます。

## 1. なぜ WebRTC 以外に無いのか

リアルタイム音声には、**遅延の制御・パケットロス補償・エコー除去・
自動利得調整・ジッタバッファ・帯域推定**が要ります。
これらを自作するのは、暗号を自作するのと同じ種類の間違いです。

WebRTC はこれを全部持っていて、**暗号が任意ではなく必須**です
（DTLS-SRTP。平文で流す設定が存在しない）。
Rinowa の「独自暗号方式を設計しない」に、ライブラリの側から合っています。

### Android の実装をどれにするか

**`org.webrtc:google-webrtc` は 2021 年で更新が止まっています。** 使いません。

| 候補 | 備考 |
|---|---|
| `io.github.webrtc-sdk:android` | upstream WebRTC の継続ビルド。素に近い |
| `io.getstream:stream-webrtc-android` | 上をラップして Kotlin/Compose 向けにしたもの |

** を採用しました。** upstream に近く、Maven Central にあります。

**APK は実測で 3.78 MB → 44.62 MB**（全ABI合計）。ABI 分割 / App Bundle で1台あたり約 14 MB。
「小さく」を掲げている以上ここは明示しますが、**通話は必須機能なので受け入れます。**

## 2. 呼び出しのやりとり（signaling）

新しいサーバーは要りません。**Firestore で足ります。**

```
conversations/{cid}/calls/{callId}
  callerId      : uid
  calleeIds     : [uid]
  kind          : audio | video
  state         : ringing | connecting | active | ended
  startedAt     : timestamp
  endedAt       : timestamp
  endReason     : hangup | declined | missed | failed | busy

conversations/{cid}/calls/{callId}/signals/{uid}
  sdp           : offer / answer
  candidates    : [ICE candidate]
```

### firestore.rules で守ること

既存のメッセージと**同じ構造**にします。参加者以外は読めない。

```
match /conversations/{cid}/calls/{callId} {
  allow read:   if uid() in get(parent).data.memberIds;
  allow create: if incoming().callerId == uid() && uid() in memberIds;
  allow update: if uid() in memberIds
                && incoming().diff(resource.data).affectedKeys()
                     .hasOnly(['state','endedAt','endReason']);
}
match /conversations/{cid}/calls/{callId}/signals/{who} {
  allow read:  if uid() in memberIds;
  allow write: if who == uid();          // 他人の SDP を書けない
}
```

**`who == uid()` が要です。** 他人の signals を書けると、
**通話を横取りできます**（自分の SDP を相手の枠に入れる）。
リアクションで「自分のキーしか変えられない」としたのと同じ規則です。

`rules-tests/run.js` に追加します。**主張ではなく実行で確かめること。**

## 3. 隠せないもの — 正直に書く

### 3.1 通話の事実は我々に見えます

本文は読めない設計を守ってきましたが、
**「誰がいつ誰に何分電話したか」は Firestore に残ります。**

signaling が Firestore を通る以上、これは避けられません。
`state` と `startedAt` / `endedAt` は、通話を成立させるために必要な情報です。

**できること**:
- **通話が終わったら signals を消す。** SDP と ICE 候補は残す理由が無い
- **通話記録を会話の一部として持つ**（「通話 3分12秒」）。
  これは**利用者に見せるため**であって、我々が集計するためではない
- **通話の集計を Analytics に送らない。** 回数も長さも

**できないこと**: 通話があったこと自体を我々から隠すこと。
`PRIVACY_PRINCIPLES.md` に「本文は読めない」と書いてあるのと同じ強さで、
**「通話のメタデータは見える」と書きます。**

### 3.2 相手に IP アドレスが渡ります

**WebRTC で直接繋ぐということは、互いの IP を知るということです。**
ICE 候補にそのまま入っています。IP からはおおよその地域が分かります。

Signal は、連絡先でない相手からの通話を**常にサーバー経由に落とす**ことでこれを避けています。

Rinowa の場合:

- 通話できるのは**既に友達追加した相手だけ**にします。知らない人から着信しない
- それでも、**友達には自分の IP が渡ります**。家族なら問題になりにくいですが、
  **仕様として書いておきます**
- TURN を持つなら「常に中継」の選択肢を設定に置けます（§5）

**「知らない人から通話が来ない」ことは、着信 UI の前に決めるべき仕様です。**
技術ではなく製品の話なので先に決めます。

## 4. 着信をどう起こすか

相手のアプリは動いていません。**FCM の高優先度データ通知**で起こします。
既存の `push.php` から送れます（通知の仕組みは既に稼働中）。

```
data: { type: "call", callId, conversationId, kind, callerName }
priority: high
```

### Android 側の制約

| 項目 | 内容 |
|---|---|
| Doze | 高優先度 FCM は Doze を貫通する。**ただし頻度制限がある** |
| 全画面表示 | `USE_FULL_SCREEN_INTENT` が要る。**Android 14 以降は通話・アラームアプリに限定**され、審査対象 |
| Foreground Service | Android 14 以降、**型の宣言が必須**。通話中は `microphone` / `camera` |
| Telecom 連携 | `ConnectionService` + `MANAGE_OWN_CALLS`。**入れると得られるもの**: система の通話UI、Bluetooth ヘッドセット、携帯電話の着信で自動保留 |

**Telecom 連携は段階2で入れます。** 無くても通話はできますが、
**Bluetooth イヤホンで応答できない通話アプリは使われません。**

### API level ≠ 端末の能力

Direct で2回踏んだ教訓をここでも適用します
（`ACCESS_LOCAL_NETWORK` の件、`DIRECT_ARCHITECTURE.md` §0）。

- `USE_FULL_SCREEN_INTENT` が実際に許可されているかは**実行時に確認する**
- 権限の存在を `PackageManager.getPermissionInfo` で確かめてから要求する
- **We2（Android 16）で必ず確認する。** Pixel だけで判断しない

## 5. TURN — 用意します

**「TURN が無いと たまに動かない」はあり得ない、というのが方針です。** 同意します。
なので TURN は「要るかどうか」ではなく「**どれにするか**」の問題として扱います。

### なぜ必要か

STUN は「自分が外からどう見えているか」を教えてくれるだけで、
**両側が対称 NAT の後ろにいると、教わった住所が相手には使えません**。
日本のモバイル回線は CGNAT が多く、この条件に当たりやすい。
一般に接続の1〜2割が失敗します。

### 選択肢と判断

| 案 | 費用 | 判断 |
|---|---|---|
| **東京の VPS で coturn** | 月 700〜900円（定額） | **採用。** 理由は下 |
| Cloudflare の TURN | 無料枠 + 従量 | 次点。運用が要らないのは強いが、下の3点で負けた |
| XServer で coturn | — | **不可。** 共有ホスティングで常駐プロセスと任意ポートは動かせない |
| managed（Twilio 等） | 従量・高い | 不要 |

### 制約: 月額の固定費は使えない

**Rinowa に継続的な支出は無い。** これは資金が不足しているという話ではなく、
**設計上の制約**として扱う。Cloud Storage を避けて Firestore の Blob にしたのも、
Blaze プランを見送ったのも同じ理由で（`ROADMAP.md`）、TURN だけ例外にはしない。

したがって判断はこうなる。

| 案 | 費用 | 判断 |
|---|---|---|
| **Open Relay（公開の無料 TURN）** | 0 | **いま入っている。まず実測する** |
| Cloudflare の TURN | 無料枠あり | **次点。** 支払い情報が要らないなら移る |
| 東京の VPS で coturn | 月700〜900円 | **技術的には最良。資金ができたら** |
| XServer で coturn | — | **不可。** 共有ホスティングで常駐プロセスは動かせない |

### 技術だけで選ぶなら VPS だった

記録として残しておく。費用の制約が無ければ東京の VPS を選ぶ。理由は3つ。

1. **利用者が日本にいる。** TURN は経路にホップを1つ足す行為で、
   そのホップを東京に固定できるならそれが最短。**遅延は通話で唯一「感じる」もの**
2. **定額で青天井にならない。** ビデオ中継は 1時間 1.3 GB。従量課金はそこで跳ねる
3. **第三者をメタデータの経路に入れない。** Rinowa は既に「通話があった事実は我々に見える」と
   明記している。そこに第三者を足すと**構造で保証できない約束**が1つ増える

`ice.php` の HMAC 経路は実装済みなので、ホストと共有秘密を入れれば動く。
**移れる状態にしてあることが、いま移らないことの代わりになる。**

### 先に測る

**TURN が要るかどうかは、まだ実測していない。**

STUN だけで繋がるのは「両側とも対称 NAT ではない」とき。
家の Wi-Fi は多くの場合そうではないので、**家 ↔ モバイルは STUN だけで通ることがある**。
必ず失敗するのは両側がモバイル回線（CGNAT）のときで、それが何割になるかは回線次第。

**お金を使う判断の前に、失敗率を数えること。**
そのために ICE 候補の種別を通話画面に出すようにした（`WebRtcSession.diagnosis()`）。

| 表示 | 意味 |
|---|---|
| `自分=host` のみ | STUN に届いていない。ネットワークが塞いでいる |
| `自分=host/srflx` | STUN は成功。相手が素直なら繋がる |
| `自分=host/srflx/relay` | 中継まで確保できた。ここで失敗するなら別の問題 |

### 帯域の見積もり

中継されるのは**直接繋げなかった通話だけ**です。それでも上限を見ておきます。

| | 片道 | 中継が扱う量 | 1時間あたり |
|---|---|---|---|
| 音声 (Opus) | 約 40 kbps | 80 kbps | **約 36 MB** |
| ビデオ 720p | 約 1.5 Mbps | 3 Mbps | **約 1.3 GB** |

家族数人なら無料枠に収まります。**ビデオを常用すると桁が変わる**ので、
そのときが VPS へ移る判断点です。

### 認証情報は必ず短命にする

**これが TURN でいちばん重要な実装上の注意です。**

> **APK に固定の TURN パスワードを埋めてはいけません。**
> 取り出されて、他人の帯域として使われます。

標準的な方法があります（TURN REST API）。
`username = 期限のUNIX時刻:uid` を作り、共有秘密で HMAC-SHA1 したものをパスワードにする。
有効期限は数分。

**発行元は `push.php` と同じ場所**です。あそこは既に Firebase の ID トークンを
検証しているので、`turn.php` は同じ手順で本人確認してから発行できます。
共有秘密はサーバーにだけ置きます。

### 中継が見るもの

TURN は SRTP を転送するだけで、**中身は復号できません**。
ただし **IP アドレスと通話時間は見えます**。
自前 VPS に移したときは、**ログを残さない設定にすること**を仕様に含めます。

## 5.5 ビデオのコーデック — 「その端末の最高の圧縮」について

**方向は正しいですが、条件が2つあります。**

### 条件1: 両方の端末が対応しているものしか使えない

WebRTC は SDP の offer/answer で**共通集合から選びます**。
片方が AV1 を積んでいても、相手が持っていなければ使えません。
つまり「その端末の最高」ではなく「**その2台の最高**」です。

### 条件2: ソフトウェアで回したら意味が無い

**重要なのは「対応しているか」ではなく「ハードウェアで符号化できるか」です。**

ソフトウェアで AV1 を 720p30 で符号化すると、CPU を数コア占有して発熱し、
サーマルスロットリングで**フレームが落ち、電池も溶けます**。
圧縮率で数十パーセント勝っても、通話としては負けです。

| コーデック | 圧縮効率 | Android のハードウェア符号化 |
|---|---|---|
| **AV1** | 最良 | **ごく最近の一部のみ。復号だけ対応の機種が多い** |
| **VP9** | 良 | 機種による。まだら |
| **H.264** | 基準 | **ほぼ全機種にある** |
| H.265 | 良 | **WebRTC では実質使えない**（ライセンス事情） |

### 決めたこと

```
ハードウェアで符号化できる中で最良を選ぶ。
両端の共通集合に無ければ落とす。
最後は必ず H.264 に落ちる。
```

**そして「対応している」を実行時に確かめてから使います。**
`MediaCodecList` に載っていることと、その端末で実用的な速度で動くことは別です。
Direct で2回踏んだ「**API level ≠ 端末の能力**」と同じ話なので、同じ扱いにします。

### ただし、コーデックより先に効くもの

正直に言うと、**画質を決めるのは主に解像度とビットレートの適応**であって、
コーデックの世代ではありません。
WebRTC の帯域推定は、回線が細れば自動的に解像度を落とします。
**ここを切ってコーデックだけ最新にしても、体感は良くなりません。**

コーデック選択は「同じ画質をより少ないバイトで」。
**「電波が悪いときに繋がり続ける」のは適応のほうの仕事です。**

### 電池はどちらに転ぶか分からない

- 圧縮が良い → 送るバイトが減る → **無線の稼働が減る**（電池に有利）
- 圧縮が良い → 符号化が重い → **CPU/GPU が回る**（電池に不利）

**どちらが勝つかは端末次第で、測らないと分かりません。**
V-3 で測ります。**推測で数字を書きません。**

## 6. Rinowa Direct との接続 — ここは強い

**同じ Wi-Fi にいるとき、通話はサーバーを一切必要としません。**

WebRTC の ICE は、まず**ホスト候補**（端末のローカル IP）を試します。
同一 LAN なら**これで繋がります**。STUN も TURN も出番がありません。

残るのは signaling ですが、これも既存の LAN transport（NSD/mDNS）で運べます。

```
同一 Wi-Fi   →  signaling も media も LAN 内。インターネット不要
それ以外     →  signaling は Firestore、media は STUN/TURN
```

**家の中の通話が、外を1バイトも通らない。** これは Rinowa Direct の思想
（`Cloud when far. Direct when near.`）が、通話でそのまま効く場所です。

### 完全オフライン（Nearby のみ）の通話は段階外

Wi-Fi インフラも無い状況（`RESEARCH_MESH.md` の世界）で、
Nearby の byte stream に音声を載せることは**理屈の上では可能**ですが、
WebRTC はそのままでは使えず、ジッタバッファから自作することになります。

**やりません。** §1 と同じ理由です。研究項目として `RESEARCH_MESH.md` 側に置きます。

## 7. 通話中の UI と操作感

Rinowa の中心は操作感なので、通話も例外にしません。

- **着信は触覚から始まる。** 音の前に手に来る。`HAPTIC_DESIGN.md` の語彙を拡張する
- **応答・拒否は誤爆しない配置にする。** 寝起きに間違えて出るのが最悪の体験
- **通話中に会話画面へ戻れる。** 小さいバーで戻れるようにする（後追いで作ると必ず歪む）
- **切断は明示的に。** 「通話が終わりました」を出す。黙って消えない

**接続中の表示を曖昧にしない。**
`呼び出し中 → 接続中 → 通話中` を出し分けます。
「繋がっているのか分からない数秒」は、通話でいちばん不安になる瞬間です。

| # | 内容 | 検証すること |

| **C-1** | WebRTC ライブラリを入れ、**Direct Lab で1対1の音声**を通す | **音が出るか。APK が何 MB 増えるか** |

**それを受け入れるかどうかを先に決める必要があります。**

## 9. やらないこと

- **通話の録音機能を作らない。** 相手の同意の問題を、こちらが作る理由が無い
- **音声を解析しない。** 文字起こしも、感情分析も、品質のための本文取得もしない
- **通話の内容をサーバーに置かない。** SRTP は端末間で終わる
- **暗号を自作しない。** DTLS-SRTP をそのまま使う
- **「繋がる」と言い切らない。** TURN の判断が済むまでは実験機能として出す
