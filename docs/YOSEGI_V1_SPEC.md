# Rinowa Original Format — Yosegi v1 — 仕様（凍結）

**状態: FROZEN 2026-08-17**
参照実装: `research/wire/yosegi.js` ／ 本実装: `android/core/wire/`

**この文書は変更しません。** v1 として固定されたものが書いてあります。
変更が必要になったら v2 を作ります。仕様を後から書き換えると、
既に配ったクライアントが何を話すのか誰にも分からなくなるので。

## 改名の記録

この形式は名前を2回変えています。**バイト列は一度も変わっていません。**

| いつまで | 名前 | 変えた理由 |
|---|---|---|
| 2026-08-19 | **EWF**（Echo Wire Format） | アプリ名が Echo だった |
| 2026-08-27 | **Rinowa** | EWF は Expert Witness Format（デジタル鑑識のディスクイメージ形式）として既に定着した略号で、衝突していた |
| 現在 | **Yosegi**（寄木） | アプリ名が Rinowa になった。「Rinowa のための Rinowa」では何のことか分からない |

2026-08-27 に一度 **Tessera**（ラテン語のモザイク片）へ動かし、同日 Yosegi に戻しました。
公開ページにも短時間出ています。**動かしたのは呼び名だけで、バイト列は触っていません。**

**凍結は破っていません。**
凍結しているのはワイヤ上の表現であって、その呼び名ではありません。
改名前に符号化されたフレームは、改名後の実装がそのまま復号します
——`YosegiCompatibilityTest` の**固定バイト列ベクタが一度も変わっていない**ことが、
その証拠です。

なぜ寄木か。寄木細工は**留め具を一切使わず、部品の形と順序だけで組み上がる**工芸です。
この形式がやっているのは正確にそれで、区切り文字も名札も詰め物も入れず、
**部品の形と並び順だけ**でメッセージを組み立てています。

読みは **ヨセギ**。

`outputs/` 以下の過去のリリースノートは **当時の名前のまま残してあります。**
0.9.0 を出荷した時点での名前は EWF、0.20.3 の時点では Rinowa。
後から書き換えたら、それは記録ではなくなるので。

## 0. Freeze 判断

凍結の条件は4つでした。すべて満たしています。

| 条件 | 結果 |
|---|---|
| Yosegi が依然として明確に優位 | **JSON 267.7 B → 98.8 B（36.9%）**、圧縮なし・5.2 µs。MessagePack と CBOR は 88% 止まり |
| 辞書 Deflate の上積みに十分な価値 | **98.8 B → 66.4 B（67.2%）**、8 KB 辞書・26 µs、**全長さ帯で膨張ゼロ** |
| 実装複雑性に見合う | 参照実装 約 300 行。ワイヤ型による前方互換あり |
| 安全性・耐障害性に問題がない | fuzz **92,362 件**で契約違反ゼロ。1件あたり最大ヒープ 0.66 MB |

数値は**現実的コーパス**（`corpus2.js`、テスト文の 68.3% が訓練に存在しない）での実測です。
合成コーパスから乗り換えても結論は変わりませんでした。

**実機確認（2026-08-17、3機種）**

| | Pixel 10 | Galaxy A23 5G（下限） |
|---|---|---|
| encode | 1.18 µs/通 | **2.80 µs/通** |
| decode | 1.70 µs/通 | **4.28 µs/通** |
| 削減率（JSON比） | 78% | **78%** |

**削減率は3機種すべてで1バイトも違いませんでした。**

この 78% は **Android 上の JSON 相当**との比較です。比較対象を書かずに出すと、
「項目名を落としただけで誰でも取れる分」と「Yosegi 自身が稼いだ分」が
混ざったままになります。分けた結果は `RESEARCH_WIRE_FORMAT.md` の追記に。
公開する数字は **MessagePack 比 60.5%**、指摘への答えは **素朴バイナリ比 41.5%**。
下限の端末でも、1通の送信で Yosegi が使う CPU はネットワーク往復の **0.005% 程度**です。
実装複雑性の条件は、この数字をもって確認済みとします。詳細は `RESEARCH_WIRE_FORMAT.md` §14。

**採用しなかったもの**: KANA8（辞書があると上積み 1.8%）、
セッション圧縮（8 B のために会話全体の耐障害性と長さ秘匿を失う）、
独自圧縮アルゴリズム（既存に敗北）。

## 1. 用途と非用途

**Yosegi が担うこと**: Rinowa のメッセージ封筒を、両端が共有している文脈を前提に短く表すこと。

**Yosegi が担わないこと**:

- **機密性** — Yosegi は暗号ではない。バイト列を持つ者は誰でもこのファイルの通りに復号できる
- **完全性** — チェックサムを持たない。壊れたフレームは多くの場合拒否されるが、**保証はしない**
- **認証** — 誰が送ったかを証明しない

> **Yosegi を唯一の門にしてはならない。**
> 完全性と認証は下の層が持つ: Cloud は TLS、Direct は Nearby の暗号化チャネル、
> E2EE 導入後は AEAD の認証タグ。AEAD がある以上、Yosegi に CRC を足すのは重複であり、
> 1通 66 B に 4 B を足す価値はない。

## 2. 共有文脈（Context）

送受信の前に両端が一致していなければならないもの。

| 項目 | 内容 | 不一致のとき |
|---|---|---|
| `conversationId` | 会話 ID | フレームには入らない。経路が決める |
| `memberIds` | 参加者 ID の**順序つき**配列 | **送信者を取り違える。** ハッシュ照合必須 |
| `stickerCatalogue` | スタンプ ID の**順序つき**配列 | スタンプ ID を取り違える |

**`memberIds` の順序は会話の属性であり、変えてはならない。**
メンバー追加は末尾に追記する。並べ替えると過去のフレームの意味が変わる。

ハッシュ照合の方法は `RESEARCH_ADAPTIVE_TRANSPORT.md` §4。
一致しない場合は索引化を使わず、完全な ID を送る（§5.2 の `0xFF` 経路）。

## 3. 基本型

### 3.1 varint

7ビットずつ、下位から。継続ビットは最上位ビット。

**最大8バイト。** それを超えたら拒否。8バイトで 56 ビットあり、
これは倍精度浮動小数点数が正確に表せる範囲（2^53）を含む。
上限が無いと、継続ビットの連続が攻撃者の忍耐だけで決まるループになる。

### 3.2 zigzag varint

符号つき。`n >= 0 ? n*2 : -n*2-1`。
時刻差分に使う。**メッセージは順不同で届くことがあり、負の差分が10バイトになってはいけない。**

### 3.3 packed id

Firestore の自動 ID は base62 の20文字（62^20 < 2^120）。
これを**15バイト**のビッグエンディアン整数として詰める。

Firebase Auth の uid は28文字（62^28 < 2^167）。**21バイト**。

長さが足りないバイト列は拒否する。

### 3.4 string

varint の**バイト長**、続いて UTF-8。

## 4. フレーム

```
frame := version(1) count(varint) baseTimestamp(varint) message*
```

| 項目 | 値 |
|---|---|
| `version` | **`0x01`**。他の値は拒否 |
| `count` | メッセージ数。**上限 4096** |
| `baseTimestamp` | 最初のメッセージの epoch ミリ秒 |

**`count` は確保の前に検証する。** 1通の最小バイト数は 19
（id 15 + 送信者 1 + 時刻 1 + 状態 1 + 終端 1）なので、
`count * 19 > 残バイト数` なら**一切確保せずに拒否**する。
長さフィールドは他人からの約束であって、事実ではない。

---

## 5. メッセージ

```
message := packedId(15) sender(1|22) tsDelta(zigzag) status(1) field* END(0x00)
```

### 5.1 packedId

15バイト。§3.3。

### 5.2 sender

1バイト。`memberIds` への索引。

`0xFF` のときは続く21バイトが完全な uid（文脈に無いメンバー）。
**索引が `memberIds.size` 以上なら拒否。** `undefined` に落としてはならない —
送信者不明のメッセージは、誰のものでもないか、あるいは黙って別人のものになる。

### 5.3 tsDelta

zigzag varint。直前のメッセージの時刻からの差（最初は `baseTimestamp` から）。
結果が正確な整数でなければ拒否。

### 5.4 status

1バイト。`0=Sending 1=Sent 2=Delivered 3=Read 4=Failed`。
範囲外は拒否。

### 5.5 フィールド

タグ1バイト = `(フィールド番号 << 3) | ワイヤ型`。

**ワイヤ型**:

| 値 | 意味 | 読み飛ばし方 |
|---|---|---|
| 0 | フラグ（本体なし） | 何もしない |
| 1 | varint | varint を1つ読む |
| 2 | 長さつきバイト列 | varint 長 + その分 |
| 3 | 固定15バイト | 15バイト |
| 5 | 複合ブロック | varint 長 + その分 |

4・6・7 は未定義。**遭遇したら拒否**（長さが分からないので以降が読めない）。

**フィールド**:

| # | 型 | 内容 |
|---|---|---|
| — | — | `0x00` = END |
| 1 | 2 | `text`（UTF-8） |
| 2 | 1 | `stickerId`（カタログ索引） |
| 2 | 2 | `stickerId`（カタログに無い場合の文字列） |
| 3 | 5 | `replyTo` = packedId(15) + senderName(string) + excerpt(string) |
| 4 | 5 | `reactions` = count(varint) + (memberIdx(1) + palette(1))* |
| 5 | 2 | `senderName`（参加者一覧で解決できない場合のみ） |
| 6 | 0 | `retracted` |

**未知のフィールド番号は、ワイヤ型に従って読み飛ばして続行する。**
これが v1 の最も重要な性質である。読み飛ばせないと、
将来フィールドを1つ足しただけで旧クライアントは
「新フィールドが見えない」のではなく**それ以降を一切読めなくなる**。
メッセンジャーではそれは「メッセージが黙って届かない」という形で現れる。

複合ブロックの中は**そのブロック長で閉じる**。
中の嘘が次のメッセージまで届いてはならない。

### 5.6 値域

| 項目 | 制約 |
|---|---|
| reaction の palette 索引 | `< 6`（`ReactionPalette.emoji` と一致） |
| sticker 索引 | `< stickerCatalogue.size` |
| reaction 数 | `count * 2 <= ブロック残バイト数` |

## 6. デコーダの契約

> **任意のバイト列に対し、正しいメッセージ配列を返すか `YosegiError` を投げるかの、どちらかしかしない。**

してはならないこと:

1. `YosegiError` 以外を投げる（境界検査の漏れを意味する）
2. 上限なく確保する
3. 上限なくループする
4. **送られていないバイトからメッセージを組み立てる**

4 が最も静かな失敗であり、この契約が厳しい理由である。
JavaScript で終端を越えて読むと `undefined` が返り、`undefined & 0x7f` は `0` になる。
つまり切り詰められたフレームから**もっともらしいメッセージが生成され**、
例外もログも無しに、人間が書いたものとして画面に出る。

検証: `research/wire/fuzz.js` — 92,362 件、契約違反ゼロ。

## 7. 圧縮（Yosegi の外側）

**フレーム全体**を DEFLATE（raw、辞書つき）で圧縮する。

| 項目 | 値 |
|---|---|
| アルゴリズム | raw DEFLATE（zlib ヘッダなし） |
| 辞書 | **8 KB**、静的・全員同一・版番号つき |
| 既定 | 有効。辞書版が不一致なら**無圧縮** |

**8 KB の根拠**（`dictsize.txt`、現実的コーパス）:

| 辞書 | B/通 | 対 生Yosegi | enc µs |
|---|---|---|---|
| なし | 98.8 | 100.0% | 0.0 |
| 4 KB | 69.6 | 70.5% | 22.5 |
| **8 KB** | **66.4** | **67.2%** | **26.4** |
| 16 KB | 64.9 | 65.7% | **104.3** |
| 32 KB | 63.7 | 64.5% | 165.0 |

**8 KB と 16 KB の間に明確な変曲点がある。** CPU が4倍になって圧縮は 2.3% しか改善しない。

辞書の作り方: 訓練コーパスから作った Yosegi フレームの連結の**末尾** 8 KB。
LZ の一致距離は近いほど安いので、価値の高い素材を後ろに置く。

**辞書に実ユーザーの発言を入れてはならない。**
理由は `RESEARCH_COMPRESSION_SECURITY.md` §4.3。

### 展開上限（必須）

| 経路 | 圧縮後 | 展開後 |
|---|---|---|
| 1通 | 64 KB | **256 KB** |
| burst / sync / bundle | 1 MB | **4 MB** |

DEFLATE の最大圧縮比は約 1032:1。**上限なしに展開してはならない。**

## 8. 順序（E2EE 導入後）

```
Message → Yosegi → deflate+dict → AEAD 暗号化 → 送信
```

逆順は不可能（暗号文は縮まない）。
メッセージをまたぐ圧縮状態は**持たない**。理由は `RESEARCH_COMPRESSION_SECURITY.md` §3。

## 9. v1 が意図的に持たないもの

| 無いもの | 理由 |
|---|---|
| チェックサム / CRC | AEAD と重複。66 B に 4 B は高い |
| 暗号化 | 別層。自作しない |
| 圧縮の内蔵 | 分離したほうが測れるし、切り替えられる |
| セッション状態 | §8 |
| 文字コードの独自化（KANA8） | 辞書があると上積み 1.8% |
| 添付・画像の本体 | ID のみ。`STICKER_ARCHITECTURE.md` |

---

## 10. v2 を作るときの条件

v1 を書き換えず、新しいバージョンバイトで作る。

v2 が必要になる可能性が高いもの:

- フィールド番号が 31 を超えたとき（タグ1バイトの上限）
- `memberIds` の索引が 254 を超える会話（現状 `0xFF` は予約）
- packed id の前提が変わったとき（Firestore 以外の ID 体系）

いずれも**今は起きない**。起きるまで v1 のまま。
