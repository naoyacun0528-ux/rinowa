# Echo 0.6.1 — 通知の修正と Echo Direct の経路制御

0.6.0 からの修正と追加。**新機能は Direct の経路選択のみ**で、あとは 0.6.0 で出た不具合の修正です。

---

## 通知の修正

### タップしても会話が開かなかった

Intent に会話 ID は載せていたのに、**受け取る側を書いていませんでした。** アプリが前面に出るだけで、開いていた画面のまま止まります。

- `MainActivity` が Intent から会話 ID を読むように
- **`onNewIntent` も実装** — 通知は起動中にタップされることのほうが多く、これが無いと2回目以降が効きません
- 会話一覧の読み込みを待ってから開きます。通知で**コールドスタート**したときは、タップの瞬間にはまだ会話が存在しないためです

### トーク画面を開いている間も通知が来ていた

目の前で届くのを見ているのに手元が震えるのは、単に邪魔です。**その会話を開いていて、かつアプリが前面にある間**は通知を出しません。

**サーバー側では判断しません。** それをやるには「誰が今どの画面を見ているか」を継続的に送り続けることになり、通知1件を減らすために集めるには重すぎる情報です。端末側なら無料で分かります。

ライフサイクル連動なので、**ホームに退避したら通知が復活**します。合成は背面でも生き残るため、画面の有無だけで判定すると、閉じている間ずっとその会話だけ黙ることになります。

### アイコンが丸い塊だった（F-52E）

**通知専用アイコンを用意していませんでした。** ランチャーアイコンの流用です。

Android は小アイコンの**色を全部捨ててアルファだけ**を使うので、不透明なアプリアイコンはベタ塗りの白い塊になります。Pixel でたまたまマシに見えていただけでした。

白＋透明で描いた専用アイコンを作りました。三重の波紋を**塗りなしのストロークだけ**で構成してあるので、シルエット化されても形が残ります。色は Echo のアクセントに着色されます。

## Echo Direct

### F-52E で探索できなかった

**`SDK_INT >= 36` で権限を要求していたのが原因**でした。arrows We2 は Android 16 を名乗りますが、**`ACCESS_LOCAL_NETWORK` という権限自体が存在しません**（`pm grant` が "Unknown permission" を返します）。存在しない権限を要求 → 拒否扱い → 探索できず、という流れでした。

`PackageManager` に**その権限が実在するか**を問い合わせる形に直しました。

> **これは触覚と同じ形の間違いです。** 同じ端末が API 36 を名乗りながら Envelope 非対応で T1 まで落ちたのと、まったく同じ。**バージョン番号は API を語るが、端末を語らない。**

### 接続が「接続失敗」になっていた

`STATUS_ALREADY_CONNECTED_TO_ENDPOINT (8003)` —— **既に繋がっていました。**

両端末が同時に広告と探索をするので、どちらが先に繋ぐか決まっていません。私のコードは「**自分が connect() を呼んだとき**」しか接続済みと数えておらず、相手から来た接続を無視していました。

- 接続状態を transport 自身から読むように（要求した記録ではなく、存在する接続を見る）
- 8003 を失敗として扱わない

**Direct は最初から成立していました。** バグは表示側だけです。

あわせて実バグを1つ修正。`requestConnection` の第1引数は「相手に見せる**自分の**名前」なのに、**相手のラベルを渡していました。**

### 新機能: 経路を選べるように

| | 挙動 |
|---|---|
| **速度優先** | 使える中で一番速い経路。同じWi-Fiにいれば Wi-Fi |
| **オフライン優先** | **Bluetooth だけ。** 遅いが、ネットワークが無くても繋がる |

`setLowPower()` / `setDisruptiveUpgrade()` を使っています（依存している 19.3.0 の JAR を `javap` で直接確認しました。ドキュメントが取得できなかったため）。

**なぜ要るか。** 放っておくと Nearby は速い経路を選ぶので、同じ Wi-Fi にいる限り Wi-Fi になります。その状態で「繋がった」と言っても、**オフラインで動く証拠にはなりません**。実質 LAN 階層を測っていることになります。

**接続中の経路も表示**するようにしました。端末名の下に `Bluetooth（オフライン可）` か `Wi-Fi（オフライン不可）` が出ます。

**Wi-Fi を破壊しないように** `setDisruptiveUpgrade(false)` を入れました。Nearby は速度のために既存の Wi-Fi 接続を切ることがあります。スタンプ1枚のために家の Wi-Fi が落ちるアプリは誰も使い続けません。

### 自動接続

相手を見つけた瞬間に繋ぎます（既定 ON）。製品では誰も「接続」を押さないので、検証画面でも押す必要はありませんでした。**トグルで OFF にできます** — 発見と接続の時間を別々に測るとき用です。

## オフライン通知について（決定: B）

**圏外では通知は届きません。** FCM はインターネットを要するので回避できません。

Direct 経由で通知を出すことは可能ですが、**Echo が生きている必要があります**。FCM が強いのは OS が受け取ってアプリを起こす点で、Direct にその仕組みはありません。

| Echo の状態 | Direct 経由の通知 |
|---|---|
| 開いている / 生きている | 出せる |
| スワイプ終了・OS に殺された | **出せない** |

3行目を埋めるにはフォアグラウンドサービスが要り、代償は**消えない常駐通知**と**継続的な電池消費**です。

**今は作りません。** 電池の実測値が無い段階で、Direct を使わない人にまで負担を負わせる判断はできないためです。ただし **Direct をやる動機そのもの（災害・圏外）は、これが無いと埋まりません。** Direct-1 で電池を測ってから、任意の3段目として足すかを判断します。→ [DIRECT_ARCHITECTURE.md §14.5](../../docs/DIRECT_ARCHITECTURE.md)

## 実機で観測したこと

**Wi-Fi を手動で切った後、両端末とも勝手に Wi-Fi が復帰しました。** その直後、切断中に送ったつもりのメッセージが届いています。

つまり **Nearby は今もまだ無線を自動で ON にしています。** そして届いたのはオフラインで届いたのではなく、**Wi-Fi が戻って接続が張り直された結果**です。

Google はこの自動 ON を**2026年後半に廃止**します。この挙動に依存した「オフラインで動いた」という結論は、廃止後に無音で崩れます。ドキュメントに観測として残しました。

**正しいオフライン検証**は、Wi-Fi を切るのではなく「オフライン優先」を選んで `Bluetooth（オフライン可）` と表示されることを確認する形です。
