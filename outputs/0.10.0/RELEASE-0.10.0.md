## 写真が送れます（ただし段階1）

**プラス → 写真を選ぶ → 会話に出ます。**

### 正直に言っておくこと

**今の版で送られるのは「32ピクセルの極小サムネイル」だけです。**
本体のアップロードは次の段階（M-3）です。

なぜこの順で作るか: 会話に写真が**出る**ことと、**本体が届く**ことは別の問題で、
前者だけでも会話は成立するからです。まずここまでを実機で見て、
気に入らない部分を直してから本体に進みます。

タップしても今は何も起きません。

### いちばん大事なのは容量ではなく EXIF

**写真には撮影場所の緯度経度が入っています。**
「家で撮った子どもの写真」を元ファイルのまま送るのは、家の座標を送ることです。

**メタデータを削除するのではなく、メタデータを持たない経路で作り直しています。**
ピクセルにデコードして WebP で再エンコードするので、**EXIF は構造的に消えます**。
削除は忘れられますが、作り直しは忘れようがありません。

向きだけは尊重しますが、**タグではなくピクセルを回転**させます。回した時点でタグは不要になるので。

### 何が送られているか

| | |
|---|---|
| 本体 | 長辺 2048px の WebP、200〜600 KB（**まだ送っていない**） |
| サムネイル | 長辺 32px、3〜6 KB。**メッセージ自体に埋め込み** |
| 一緒に運ぶもの | 内容ハッシュ、縦横、本体のバイト数 |

縦横を先に運ぶのは、**画像が届く前に場所を空けておく**ためです。
これが無いと写真が届くたびにスレッドが組み替わり、
**読みかけのメッセージが画面外へ飛びます。**

## 動画は入れていません

作れないからではなく、**画像を完成させる前に始めると両方中途半端になる**からです。

動画には画像に無い問題が全部あります — 1分で50〜200 MB、端末ごとに違う再エンコード、
数十秒かかる処理の途中でアプリを閉じられたときの扱い、95%で切れたアップロードの再開。
段階2で扱います。方針は `docs/MEDIA_ARCHITECTURE.md` §6 に書きました。

## 通話は設計だけ

`docs/CALLS_ARCHITECTURE.md`。実装は入れていません。**先に決めるべきことが2つあるためです。**

**1つ目: TURN サーバーが要るかどうか。**
STUN だけの WebRTC は、両側が対称 NAT の後ろだと**繋がりません**。
日本のモバイル回線は CGNAT が多く、この条件に当たりやすい。
一般に1〜2割が失敗します。**「たまに繋がらない通話」は壊れているのと同じ**なので、
実測してから判断します。XServer の共有ホスティングでは TURN は動かせません。

**2つ目: APK が何 MB 増えるか。**
WebRTC のネイティブライブラリは大きく、**現在 release 3.8 MB が倍以上になる可能性**があります。
「小さく」を掲げている以上、これは受け入れるかどうかを先に決めるべき数字です。

### 隠さずに書いたこと

- **通話の事実（誰といつ何分）は我々に見えます。** signaling が Firestore を通る以上避けられません。
  本文が読めないのとは別の話なので、`PRIVACY_PRINCIPLES` と同じ強さで明記します
- **相手に IP アドレスが渡ります。** 直接繋ぐとはそういうことです。
  だから通話できるのは**友達追加済みの相手だけ**にします
- **同じ Wi-Fi にいるときは、通話が外を1バイトも通りません。** これは Echo Direct の思想が
  そのまま効く場所です

## 安全側

写真のルールを Firestore に**反映済み**です。テストは **38件全通過**（既存29 + 写真9）。

いちばん効いているのは**サムネイルの 8 KB 上限**です。
ここは「画像の一部を文書に入れる」唯一の例外なので、
**上限が無ければこの穴から画像を丸ごと押し込めます。**

取り消しはサムネイルも消します。**「取り消しました」と表示しながら写真が見えていたら、
取り消し機能が無いより悪い**ので。

## 見つけた不具合（別件として登録）

`sendFailed` が設定されるだけで**どこにも表示されていません**でした。
つまり**メッセージ送信に失敗しても、画面には何も出ません**。
写真は同じ轍を踏まないよう、準備中も失敗も出すようにしてあります。
