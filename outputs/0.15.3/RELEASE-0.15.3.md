# Lowan 0.15.3

**Pixel 10 で E2EE が1往復しました。** `round trip OK — 復号一致`。

この版は、その計測の**読み方が間違っていたのを直したもの**です。

## 出た数字と、その正しい読み方

```
open          182 ms
plaintext     24 B
ciphertext    447 B
encrypt       46616 us
decrypt       21271 us
```

**encrypt 46.6 ms を「1通あたりの費用」と読んではいけません。**

初回の暗号化には、1回きりの作業がまるごと入っています——鍵の公開、
ワンタイム鍵の取得、ルーム鍵の配布。**どれも Firestore への往復を含みます。**
つまりこの 46 ms のほとんどは**演算ではなくネットワーク**です。

これをそのまま載せるのは、per-frame の数字を per-message の平均の隣に置いた
Rinowa 研究の誤りと**同じ形**です。

**検証を、初回と定常に分けました。** もう一度押していただくと:

```
--- 初回（鍵の配布を含む・往復あり）---
--- 定常（セッション確立後・20回平均）---
```

の2組が出ます。**採否の判断に使うのは下です。**

## 一方、これはそのまま効く数字です

**24 B の本文が 447 B になりました。約 18.6 倍。**

Megolm のイベントは base64 の暗号文に加えて session_id / sender_key / device_id /
algorithm を持ちます。**本文が短いほど比率は悪くなります。**

これは Rinowa の前提を揺らします。

| | 1通あたり |
|---|---|
| Rinowa が削った量 | 約 170 B |
| **E2EE が足す量** | **約 420 B** |

**形式を変えて削った 78% を、暗号化の固定費が上回ります。**

Rinowa を捨てる理由にはなりません——効くのは Direct と一括エクスポート、
つまり**同じ鍵材料を繰り返さない経路**だからです。ただし
「Rinowa で 78% 削減」を E2EE 込みの数字として使うことは、もうできません。
再測定は Direct-2 のときに行います。**今は推測で書きません。**

## 覚えておくこと

0.15.0 と 0.15.2 で直した2つのバグは、**どちらも release でしか出ませんでした。**

- AAR の `proguard.txt` が 0 バイトで、R8 が JNA を削っていた
- `runCatching` が `CancellationException` を捕まえ、例外名が難読化されていた

**今後、暗号まわりの実機確認は release 版で行ってください。**
debug では R8 が走らないので、通っても何の保証にもなりません。
