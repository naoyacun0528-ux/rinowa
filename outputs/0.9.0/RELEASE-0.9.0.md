## EWF v1 を凍結し、実装しました

メッセージの送信形式です。**アプリの動作は何も変わりません**（全フラグ off）。

### 何が分かったか

**1通 240 バイトの JSON のうち、本文は 26.7 バイト（11%）でした。**
残りは `senderId` と `conversationId` と ID と13桁の時刻 — **相手が既に知っていること**です。

EWF はそれを言いません。会話を開いている時点で参加者は分かっているので、送信者は**1バイトの索引**。
結果、**JSON の 23.8%** になります。

### 独自圧縮アルゴリズムは、作って、測って、捨てました

3案作りました。全部負けました。

- **ETX**（独自算術符号）→ 自作の簡易案にすら負けた
- **ETX2**（order-2）→ **知っている文でしか勝てず**、モデルが 273 KB
- **KANA8**（日本語1バイト符号）→ 辞書があると上積み **1.8%** → 保留

勝ったのは **`java.util.zip.Deflater.setDictionary`** — Android に最初から入っているものです。
追加依存ゼロ。

### 短文では zstd も brotli も payload を大きくします

7文字以下のメッセージ（全体の30%）で:

- brotli → **100% が膨張**
- zstd → **98% が膨張**
- **deflate + 事前辞書 → 一度も膨張しない**

平均圧縮率で数%勝つことより、**送ったものが必ず小さくなること**を採りました。

## Fuzz で実バグを1件見つけました

デコーダに 92,362 通りの壊れたデータを投入しました。
切り詰め・全ビット破壊・巨大な宣言長・無限に続く数値・不明なバージョン・純ノイズ。

**1件見つかりました。** 未知のフィールド型が、専用の「不正データ」例外ではなく
素のエラーを投げていました。**1ビット反転で到達する**ので、
これは「電波が悪かった」であって「アプリの障害」ではありません。
直さないと、**電波状況の悪化がクラッシュレポートの山に見えます。**

## 実装中に、測定だけでは分からなかったことが1つ

**EWF を Firestore に使ってはいけない、と分かりました。**

`firestore.rules` の保証は**フィールド単位**で動いています。
取り消しは「`retractedAt` を足して本文を消す」ことしか許さない、
リアクションは自分のキーしか変えられない、という具合です。

**1つの塊にすると、これらのルールは中身について何も言えなくなります。**
「管理者を主張するトークンでも本文を読めない」という検証済みの構造的保証が、
**クライアントの行儀への期待に格下げされます。**

**1通200バイトのために、その取引はしません。**

EWF を使うのは、経路が本当にバイト列で規則エンジンが見ていない場所だけです —
**Direct（本命）、Mesh、機種変の一括転送**。
