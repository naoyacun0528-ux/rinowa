# Lowan 0.19.0

外部レビューの指摘のうち、直せる3件を直しました。アプリの導入と規則の配備は済んでいます
（「配備しました」の節）。

## 1. 参加者を勝手に増減できた（最重要）

`firestore.rules` の会話の update は、変更してよいキーに `memberIds` を含めながら、
中身に条件を付けていませんでした。判定は「**変更前の**文書に自分がいるか」だけです。

その結果、**会話の参加者は誰でも会話に入れられました**。承認については「自分の分しか
足せない」と厳密に書いてあったのに、参加そのものが空いていました。承認を偽装できない
ことは、参加を偽装できるなら意味がありません。

エミュレータで再現したところ、通ってしまったのは3つです。

| やったこと | 直す前 | 直した後 |
|---|---|---|
| 第三者を会話に足す | 通る | 拒否 |
| 相手を会話から追い出す | 通る | 拒否 |
| 自分を他人に差し替える | 通る | 拒否 |
| 部外者が自分を足す | 拒否 | 拒否 |
| 自分だけ抜ける（脱退） | 通る | 通る |

**「相手を追い出せる」と「自分を差し替えられる」は指摘に無かったぶんです。**

参加者の変更として認めるのは「自分が抜ける」の1手だけにしました。増えていないことと、
減ったのが自分だけであることの両方を見ます。片方だけだと差し替えが通ります。作成後に
人を足す経路はアプリにありません（direct は2人固定、group は作成時に決まる）。

### 過去のメッセージについて

入れられた側が読めたのは**暗号文**です。`historyVisibility = JOINED` なので、参加前の
セッション鍵は配られません。**規則が破られた線を E2EE が押し留めていた**形です。
読めたのは足された瞬間以降で、送信もできました。

## 2. ワンタイム鍵が端末ごとに分かれていなかった

`users/{uid}/oneTimeKeys/` という利用者ごとの1つの束に置き、**鍵 id をそのまま文書 id に
していました**。Olm の鍵 id は端末の中で数える連番なので、同じアカウントの2台目が公開した
瞬間に1台目の鍵を上書きします。取り違え以前に在庫が壊れます。

さらに取得側 (`claimKeys`) は、端末を指定して要求されているのに `takeOneKey(user)` を
呼ぶだけで、端末で絞っていませんでした。KDoc には「端末ごとに1つ取り」と書いてあります。

置き場所を `users/{uid}/cryptoDevices/{deviceId}/oneTimeKeys/` に移し、取得も端末で
絞るようにしました。症状は「2台持ちの人にだけ、ときどき届かない」なので、機種変更や
再インストールの検証を始める前に直しておく必要がありました。

旧パスに残っている鍵は、新しい規則ではどこからも読めません（規則に包括の許可が無いため、
一致しないパスは既定で拒否）。公開鍵なので放置して害はありませんが、いずれ掃除します。

## 3. 途中で切れたアップロードが再開できなかった

クライアントは必ず offset 0 から送り、サーバーが 409 で返す「ここまで持っている」を
読んでいませんでした。コメントには「あとから拾い直す送信ならそこから再開するのが
正しいが」と書いてあり、**わかっていて後回しにした**箇所です。

409 の `expected` を読んで、そこまで読み飛ばしてから続けるようにしました。

受けるのは**1個目だけ**です。2個目以降で食い違ったら、それはいま書いているファイルに
ついて認識がずれたということで、続けると穴を書き込みます。穴のあるファイルもハッシュは
取れて保管され、数か月後に復号できず、原因を指すものが残りません。

読み飛ばしには単体テストを4件付けました。`InputStream.skip` は要求より少なく進んでよい
と契約に書いてあり、少なく進むのは遅い記憶装置のときで開発機では起きません。間違えると
**中身のずれたファイルが正しいハッシュの名前で保管される**——転送は成功し、画面には何も
出ません。だから端末の外で試します。

## 直していないもの

**端末検証（クロスサイニング・検証UI）はそのままです。** `onlyAllowTrustedDevices = false`
で、未検証の端末を許しています。理由はコードに書いてあるとおり、確認画面がまだ無いので
拒否すると全部拒否になるからです。これは発見された欠陥ではなく記録済みの現在地で、
別プロジェクト規模の作業です。

実務上の意味は1つ、**「管理者も絶対に読めない」と外向きに言えるのはまだ先**ということ
です。「サーバーに本文が無い」までは、いまの実装で言えます。

## 配備しました（2026-08-25）

手順どおり、アプリを先に、規則を後に入れました。

1. Pixel 10 と arrows We2 に 0.19.0（release）を導入
2. `firebase deploy --only firestore:rules --project echo-cfe37` → released
3. 実機で確認
   - 既存のスレッドがそのまま復号できる
   - Direct Lab の E2EE 往復確認：**round trip OK − 復号一致**（初回 encrypt 204ms /
     定常 encrypt 8.3ms・decrypt 3.7ms）
   - Pixel → We2 に送信 → 受信側で復号して表示
   - **Firestore の拒否は両端末とも0件**（We2 に出ていた 25 件の PERMISSION_DENIED は
     すべて端末のモデム関連で、Lowan とは無関係）

配備前の規則は `outputs/0.18.9.2/lowan-0.18.9.2-source.zip` の中にあります。戻すなら
そこから `firestore.rules` を取り出して同じコマンドを打ちます。

## 配備の順番（重要）

**アプリを先に、規則を後に。** 逆にすると、古いアプリは鍵を公開できなくなります
（旧パスが拒否されるため）。新しいセッションが張れず、症状は「ときどき届かない」です。

1. 両方の端末に 0.19.0 を入れる
2. `firebase deploy --only firestore:rules`
3. 2台で送受信して、鍵が新しい場所に出ていることを確認

参加者についての規則の変更は、古いアプリでも問題ありません（脱退は通ったままで、
ほかに `memberIds` を書く経路がないため）。順番が要るのは鍵のほうだけです。
