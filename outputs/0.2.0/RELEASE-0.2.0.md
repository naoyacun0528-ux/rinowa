# Echo 0.2.0

2026-08-15 / Prototype 0 / Android only

**スタンプを主要機能として追加しました。**
あわせて、クラウド接続を将来入れても壊れない形のデータモデルと設計文書を用意しています。

---

## 触ってわかる変更

### スタンプが送れる

コンポーザー左のスタンプボタンからパネルが開き、タップするとその場で送信されます。
選んでから確定という2段階にはしていません。スタンプは1つの表現行為であり、
2タップにすると入力フォームになってしまうためです。

組み込みスタンプ8種（いいね / ありがと / OK! / うける / ごめん / たすかる / おつかれ / まってる）。

**スタンプには吹き出しが付きません。** 吹き出しで包むと「送られた画像」に見え、
表現そのものとして読めなくなるためです。

---

## 見えないが重要な変更

ここが今回の本体です。**見た目より、後戻りできない部分を先に正しくしました。**

### メッセージはスタンプ画像を運ばない

```
❌ message { type: STICKER, imageBase64: "iVBORw0KG..." }
✅ message { type: STICKER, stickerId: "st_iine" }
```

同じスタンプを1,000回送っても、画像は1回も複製されません。

この形を Prototype 0 の今のうちに確立したのは、**後から直すのが極めて高くつく**ためです。
一度メッセージへ画像を埋める設計で動き出すと、会話の読み込みが重くなり、
将来 E2EE を入れるときに本文と添付を分離できなくなります。

### ローカルスタンプストア

受信側は `stickerId` を見て自分の端末を確認します。

```
HIT  → 即座に描画（通信なし）
MISS → 一度だけ取得 → ハッシュで検証 → 端末へ保存 → 描画
```

**送信者は「相手がこのスタンプを持っているか」を確認しません。** ID だけ送ります。

保存先は `filesDir` であり `cacheDir` ではありません。
Android は容量が逼迫すると `cacheDir` を予告なく消すため、
そこに置くと**通信できない場所でスタンプが表示できなくなります。**

Prototype 0 にはバックエンドが無いので MISS 経路は常に失敗を返します。
形だけ先に用意してあるので、Prototype 1 では中身を書くだけで済みます。

### SHA-256 による完全性

各アセットは content hash を持ちます。取得したバイト列が期待どおりかを確認するためです。

**ハッシュは暗号ではありません。** 秘密情報として扱わず、
「ハッシュを知っている＝アクセス権がある」という設計にもしません。

## プライバシー

### `stickerId` を Analytics へ送りません

カスタムスタンプの ID は、そのユーザーが自分で作った固有の資産を指します。
送れば「誰が何を作り、いつ誰に送ったか」が計測系から復元できてしまいます。

```
sticker_sent { sticker_kind: BUILT_IN }     ✅
sticker_sent { sticker_id: "st_7f3a..." }   ❌
```

`pack_id` も送りません。グループ限定パックの ID は所属関係を示すためです。

型でも守られています。`:core:analytics` の公開 API には `String` を受け取る経路が無く、
`AnalyticsEnum` は sealed なので、モジュール外から任意の文字列を作ることもできません。
**ID を送るコードはそもそもコンパイルが通りません。**

### 元写真をアップロードしない（方針として確定）

カスタムスタンプ作成の画像処理は端末内で完結させ、完成した小容量の画像だけを送ります。

これはコストではなくプライバシーの話です。元写真にはスタンプにした部分以外が写っています。
背景、写り込んだ他人、Exif の位置情報。送れば、それらを送ったことになります。

背景除去も OS のオンデバイス機能を優先し、クラウド AI を必須にしません。

### Cloud Backup は本文閲覧の理由にならない

アカウント同期を将来入れても、管理者がメッセージ本文を読める機能は追加しません。
**預かることと、読んでよいことは別です。**

## 触覚

スタンプ送信時は既存の `send` が鳴ります。それ以上は今回入れていません。

将来の Expression（スタンプ + アニメーション + 触覚）については、
**受信側の安全設計だけ先に決めました。**

> 送信者が選べるのは semantic type だけ（CELEBRATION / LAUGH / LOVE / SURPRISE）。
> 受信側が自分の設定と端末に応じて安全なパターンへ変換する。

送信者が振動時間や強度を直接指定できる構造は作りません。作れば嫌がらせの道具になります。
