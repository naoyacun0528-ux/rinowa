# Echo 0.6.0 — グループ・既読・通知・Echo Direct

---

## グループ

一覧右下の **＋を押すと2つに開きます**。

| | |
|---|---|
| **友達を追加** | これまで通り、招待コードで1対1 |
| **グループを作る** | 名前をつけて、複数人を選ぶ |

＋は押すと45度回って×になります。同じボタンの別の状態であって、上に新しいボタンが出るのではありません。

**選べるのは、既に1対1で話したことのある人だけ**です。Echo には「友達申請」という手順が無く、**招待コードを交換して話すこと自体が関係の成立**なので、別に友達リストを持つと二重管理になります。二重にすると、片方が必ず先に古くなります。

家族で使うなら：各自と1対1で招待コードを交換 → グループにまとめる、の順です。

招待された側の文面もグループ用に分けました。グループに「友達に追加」と出すのは、起きていないことを説明することになるので。

| | 1対1 | グループ |
|---|---|---|
| 見出し | 「○○さんからのメッセージです」 | 「『家族』に招待されています」 |
| ボタン | 友達に追加 | 参加する |

## 既読

**チェック2個をやめて「既読」の文字**にしました。送信済みのチェックも1個に減らしています。2個目は「配信済み」の意味でしたが、誰も頼んでいない区別で、しかも読めませんでした。

- 既読がつくと文字がバネで少し弾んで出ます
- そのとき **`ReadReceipt` という新しい触覚**が鳴ります。**指以外が起こす唯一の触覚**なので、いちばん弱く、1秒に1回までに絞ってあります
- グループでは**いちばん遅い人**に合わせます。5人中1人が読んだだけで「既読」と出すのは、インターフェースがつく嘘です

## 友達追加の承認

会話に `acceptedBy` を持たせました。送られた側は**スレッドは読めますが、コンポーザーの代わりに「友達に追加」が出ます**。読めなくしなかったのは、何に招待されているか分からないまま判断させることになるからです。

ルールで「自分の分しか承認できない」を強制しています。

## すべて既読

未読があるときだけ一覧の上部に出ます。**メッセージ本文は1件も取得しません** — 既読は「人ごと・会話ごとのタイムスタンプ」なので、バッジを消すのは書き込みであって、誰かのメッセージを読む動作ではありません。

## 受信時の自動スクロール

相手が画面を開いたまま受信したとき、スレッドが下まで追従します。アプリが開いている＝通知が鳴らないので、ここだけ何も知らせるものが無い状態でした。

**下端付近にいるときだけ**です。過去を遡って読んでいる人を最新まで引っ張るのは、読んでいる途中で画面を奪うことになります。

## 通知

**Android 側は完成。サーバー側は反映待ち（下記）。**

- 初回起動時に権限を要求。Echo Direct の権限とは扱いを分けています
- FCM トークンを `users/{uid}/devices/` に登録。**Echo Direct の Trusted Device と同じ場所**なので、端末を失くしたとき片方だけ消し忘れる事故が起きません
- **データのみ通知**を受け取り、端末側で通知を組み立てます
- プライバシー画面に「通知にメッセージの内容を表示する」を追加（**既定オン**）

> 既定でオンにしたのは、それが LINE と同じで期待値だからです。オンのあいだ**本文が FCM を通る**ことは画面に書いてあります。判定は**受信者の設定**で行います — 自分のロック画面に何が出るかは自分が決めることなので。

`push.php` は **`messages` コレクションを一切読みません。** 通知本文は送信者のリクエストから受け取り、その送信者が本当にその会話の参加者かを `conversations` で検証します。サーバーが他人の履歴を覗く経路は作っていません。

## Echo Direct（Android 実装）

> **Cloud when far. Direct when near.**

設計は [DIRECT_ARCHITECTURE.md](../../docs/DIRECT_ARCHITECTURE.md) と
[DIRECT_THREAT_MODEL.md](../../docs/DIRECT_THREAT_MODEL.md)。

2階層を実装しました。

| | オフライン | iPhone | 状態 |
|---|---|---|---|
| **Nearby Connections** | ○ | × | 実装済み |
| **同一LAN (NSD + TCP)** | × | **○（将来）** | **Pixel で接続確認済み** |

同一LANは Android 同士でも動きます。**将来 iPhone が繋がるのはこの経路**なので、iPhone を用意する前に道の検証ができます。

アカウント → **Echo Direct（検証中）** から開けます。**画面を開くと自動で探索を始めます** — 製品でも押す操作はありません。

### 分かった制約

**Android ↔ iPhone は「同じWi-Fi」でしか成立しません。** Nearby の iOS SDK は Wi-Fi LAN medium のみ対応で、iOS はバックグラウンドで service UUID を非公開領域に入れるため Android から BLE で発見できません。災害・圏外の場面では Android 同士・iPhone 同士のみです。

## つまずいた記録

**API レベルは端末の実態を語りません。** 2回同じ形で外しました。

- 触覚: arrows We2 は Android 16 なのに `Envelope` 非対応で **T1 Predefined** まで3段落ちる
- 権限: 同じ Android 16 でも **We2 には `ACCESS_LOCAL_NETWORK` が存在しない**（Pixel にはある）

前者は振幅制御が無いため、Success / Warning / Error が同じ感触に潰れます。**長さで区別する経路**（`HapticSpec.onOff`）を足しました。

後者は Nearby が `INTERNAL_ERROR (8)` という無意味なコードを返すため、原因究明で2回外しました。答えは logcat の1行にありました。**Play services が無意味なコードを返しても、まずログを読むこと。**

## サーバー

| | |
|---|---|
| ホスト | XServer（`nextlab.blog`）。**ブログのファイルには一切触れていません** |
| サブドメイン | `echo.nextlab.blog` 新規作成・SSL 有効 |
| PHP | 8.5 |
| 鍵 | Echo 専用の SSH 鍵を発行（Codex のものとは別。片方だけ失効できます） |
| API キー | `echo-push` / 2027-08-16 まで / **課金操作の権限なし** |

**`push.php` は稼働しています。**

```
GET  → 405 {"error":"method"}     ← 正常。動作確認はこれで足ります
POST 認証なし     → 401 {"error":"no_token"}
POST 偽トークン   → 401 {"error":"bad_token"}
```

認証が効いていることを確認済みです。誰でも通知を撃てる口にはなっていません。

確認方法： ブラウザで https://echo.nextlab.blog/push.php を開く。
`{"error":"method"}` と出れば正常、エックスサーバーのページが出れば異常。
