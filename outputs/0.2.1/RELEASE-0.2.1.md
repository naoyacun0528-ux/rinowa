# Echo 0.2.1

2026-08-15 / Prototype 0 / Android only

**可変リフレッシュレート（1Hz〜144Hz）対応。** 機能の追加はありません。

---

## 何が変わったか

### フレームレートを固定値として扱わなくなった

パネルは、常時表示中の 1Hz から高リフレッシュ端末の 144Hz まで幅があり、
**アプリが動いている最中に変わります。**

コードとドキュメントから 60Hz / 120Hz / 16.7ms / 8.3ms といった固定値を排除し、
**フレーム予算は常に実測レートから計算**するようにしました。

```
frameBudgetMs = 1000 / 実際のリフレッシュレート
```

守るべき性質は2つです。

- **固定のミリ秒を書かない**
- **フレーム数で何かを駆動しない。** アニメーションは時間基準にする。
  そうでないと 1Hz でアニメーションが止まり、144Hz で倍速になります
  （Compose の spring / tween は元から時間基準です）

### 動いているものにだけ高レートを要求する

Compose 1.12 の `Modifier.preferredFrameRate()` を使い、**実際に動いている要素にだけ**
パネルの最高レートを要求します。

| 要求する場面 | 要求しない場面 |
|---|---|
| スレッドをスクロールしている間 | 停止して読んでいる間 |
| バブルをスワイプしている間 | 静止しているバブル |
| リアクションピッカーが出ている間 | 通常表示 |

アプリ全体に常時最高レートを要求する作りにはしていません。
**メッセージを読んでいる間 120Hz を掴み続けるのは、電池を黙って奪う行為**であり、
「不要なものを押し付けない」という方針に反します。

### Haptic Lab に表示情報を追加

`画面のリフレッシュレート` セクションを追加しました。

```
現在            120.0 Hz
1フレームの予算  8.33 ms
対応レート       20 / 24 / 30 / 40 / 60 / 120
可変(ARR)       非対応（モード切替のみ）
```

**Pixel 10 は連続可変ではなく、離散モードの切り替え**でした（`hasArrSupport = false`）。
連続可変の端末では `可変(ARR) 対応` と表示され、同じコードがそのまま動きます。

## 測定結果

同じ操作（46件のスレッドを約8秒スクロール）での比較です。

| 指標 | 0.2.0（ヒントなし） | 0.2.1（ヒントあり） |
|---|---|---|
| Janky frames | 1.67% | 2.55% |
| 50th percentile | 6 ms | 6 ms |
| 90th percentile | 11 ms | 12 ms |
| 95th percentile | 15 ms | 16 ms |
| 99th percentile | 31 ms | 32 ms |

**実質的に変化なし**（差は測定ごとのばらつきの範囲）。悪化はしていません。

### 副産物: GPU にはかなり余裕がある

今回の測定で GPU 側の内訳が取れました。

```
50th gpu percentile   1 ms
90th gpu percentile   2 ms
99th gpu percentile   2 ms
```

**遅いフレームの原因は GPU ではなく UI スレッド側**です。GPU は 8.33ms の予算に対して
2ms しか使っていません。

これは NEON GLASS UI の検討に直接効きます。
私は当初「余裕が薄いのでガラスは厳しい」と書きましたが、**これは総フレーム時間だけを見た
誤った読みでした。** NEON INSTINCT の 9ms は GPU 律速の数値で、Echo の 11ms とは意味が違います。
**ガラスが消費するのは主に GPU 時間であり、そこは空いています。**

判断材料を更新済み → `design/neon-glass-ui/INTEGRATION_NOTES.md`
