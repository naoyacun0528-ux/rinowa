## Pixel 10 の実測、ありがとうございました

```
  encode      1.18 us/msg
  decode      1.70 us/msg
  sustained   332,084 msg/s
  reduction   78%
```

**デスクトップ比で encode 4.1倍、decode 1.7倍遅い。予想通りの幅でした。**
圧縮率（78%）は**デスクトップと完全に一致**しています。
「圧縮率はハードウェアに依存しないが時間は依存する」という前提が、そのまま確認できた形です。

### この数字が意味すること

**1通の送信で EWF が使う CPU は 1.18 µs。**
同じ送信のネットワーク往復は数万〜十数万 µs です。**送信全体の 0.001% 程度**で、
検討事項になりません。

**500通のスレッドを開く decode は 0.85 ms。**
120 Hz の1フレームが 8.3 ms なので、**スレッドを開いてもコマは落ちません。**

## 表示のバグを直しました（この版の主な変更）

前の版はこう出ていました。

```
  encode  1.18 us/msg   worst 778.6
```

**`worst` は1通ではなく500通フレーム全体の時間**なのに、1通あたりの平均と同じ行に並べたので、
**「1通に 780 µs かかることがある」と読めてしまいます。そんなことは一度もありません。**

正しく並べるとこうです。

| | 平均フレーム | 最悪フレーム | 比 |
|---|---|---|---|
| encode | 590 µs | 778.6 µs | **×1.3** |
| decode | 850 µs | 2225.5 µs | **×2.6** |

encode は誤差の範囲、decode は計測窓に GC が1回入った程度。**病理ではなく普通のばらつき**でした。
0.9.1 では平均と最悪をフレーム単位で並べ、倍率も出します。

`allocated` も `heap growth` に改名しました。**「確保していない」ではなく「残していない」**という意味なので。
20万個のオブジェクトを作って全部回収された結果の 0 KB です。漏れは無いが、ゴミは出ています。

## お願い — arrows We2 でも測ってもらえますか

**USB が壊れていても測れます。** 画面のボタンなので、アプリを入れて
Direct Lab →「計測」を押すだけです。

**We2 のほうが遅い端末なので、下限としてはそちらのほうが重要です。**
Pixel 10 だけで「速い」と判断すると、実際に使われる下の方の端末を見落とします。
